# Bounded offline reading and official semantic position memory

Status: implemented with source and contract validation; real browser and physical-device acceptance remain separate release evidence.

## Problem and ownership

Mobile browsers may discard a background tab or reload while a remote Host is unavailable. Keeping a transcript only in the live graph loses both the body and the user's reading position. Reopening the same Pane should recover previously authorized content without waiting for the transport, then reconcile with the source using its existing epoch and version.

HHPI owns the optional durable source-page cache. The official DSH Conversation assembler, Chat reader, virtualizer and window-publication coordinator continue to own rendering, admission and scroll correction. Native execution, approval and send identities do not come from this cache.

## Persistence boundary

The cache is partitioned by the authenticated installation/account storage scope supplied by the Host. The federation graph's storage layer also partitions Host identity. A fresh client loads a cache only after this scope is present in its authenticated bootstrap; it does not infer authorization from a session ID, origin alone or old credentials. Source identities and strict page/session schemas are checked again when loading. Production `hapi-dsh-session-provider` passes `browserSourceStorage()` to `RemoteSessions`; the owner index injects `__HHPI_STORAGE_SCOPE__`, and authenticated catalogs provide the canonical installation/principal digest for other principals. A catalog from a retired scope is cancelled and cannot move the active reader back to the previous account.

At most eight sessions and eight Pane windows per session are stored, with a 1 MiB per-session and 4 MiB total body budget. Writes are coalesced for 750 ms and flushed on `pagehide`, hidden-document transitions and disposal. Storage failures remain an optional-cache failure, and eviction touches only this cache's own keys. Drafts and operation receipts are never removed to make room.

Only officially published reader windows are saved. A prepared or rejected navigation must not replace the accepted window or pair a new body with an old position. If a live source version has not reached all displayed readers, the previous coherent checkpoint remains durable until publication catches up. Large windows may be replaced only with complete, source-produced pages containing their explicit context dependencies; event arrays are never sliced into a fabricated turn. If no complete replacement fits, retain the preceding valid checkpoint for that epoch. An accepted epoch replacement invalidates the old checkpoint immediately, including when its new body cannot be read or fit.

Initial cached bodies and each Pane's accepted range hydrate the same `RemoteSourceHistory`, then follow from the saved source cursor. A journal gap obtains an authoritative source baseline and uses the existing reader-preserving recovery path. Late pages retain the same generation/version checks as live reads. Closing a Pane preserves its durable body and does not terminate the native session. Explicit removal, access revocation or an authenticated storage-scope change clears the affected cache; a temporary connection failure does not. Complete pairing inventories invoke explicit Host revocation before ordinary graph disposal. Queued, offline and late booting Hosts also clear only their own HHPI reading/outbox keys; ordinary page close preserves them, and plugin drafts/preferences remain intact.

## Optional official Chat contract

The L2 source change introduces `chatScrollMemory.forBinding(binding)`. A hosting shell may return `read()` and `save(position)` for the official `ChatScrollPosition`. Without a provider, Chat keeps its existing in-memory map. The feature can also be independently disabled with `__DSH_CLIENT_READING_MEMORY = 'off'` or `DSH_CLIENT_READING_MEMORY=off` before the Chat view is injected.

HHPI keys positions by source identity and the persistent workspace Pane ID. It deliberately keeps the runtime reading-occurrence ID separate: its sequence changes when a Pane remounts. The stored position retains the exact anchor, semantic owner, relative top and original scroll offset, so the official virtualizer performs restoration. An old binding captures its original cache owner and cannot save into a replacement account or Host scope during delayed unmount.

The change is generated by `scripts/dsh-ext/reading-memory.mjs` against pinned upstream commit `1f81c047fc48fa190a683e469daa699857e9afe8`. Preparation checks each source seam and includes the generator in the source-input hash and generated patch manifest. No compiled bundle is rewritten and no runtime method is intercepted. Host and Runner must install the same fingerprinted extension set.

## Verification and limits

Production cache/history tests exercise process-style reload, independent Pane ranges, failed storage, bounded eviction, same-instance reopen, rejected navigation and immediate epoch invalidation. The official Chat contract executes the prepared pinned source or the installed extension, asserting semantic position storage, independent Pane keys, stale-scope save rejection and the unchanged disabled/default path. Source RPC, browser storage and settings are controlled test boundaries; fake DOM geometry does not establish mobile scroll behavior.

This cache does not install a service worker or cache authenticated HTML, tokens or the application shell. It restores reading after the application starts from an available or browser-cached authenticated bootstrap. A completely offline first load with no application assets cannot be made usable by transcript persistence alone.

Source-page records retain attachment references, not binary image or file resources. Resource availability still follows the source's existing authenticated access path and any browser cache already held for it.
