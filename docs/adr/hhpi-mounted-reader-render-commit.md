# Acknowledging the payload rendered by an official Chat node

A source snapshot can replace a node while retaining its key and reading anchor. The source publication can arrive before React commits the new body. A DOM key, a reading-facts revision or a completed animation frame therefore cannot prove that the user could read the new payload.

The pinned ui-chat extension adds optional `renderedNodes: 1`, `MountedChatV1.renderedNode(key)` and `ReadingSnapshotV1.renderRevision`. A Node seat registers its exact public conversation-node object in its layout effect and withdraws that object on cleanup. The existing mounted-control subscription announces these changes. Concurrent seats share a counted lease; cleanup for an older object cannot withdraw its successor. ChatView does not subscribe to these per-node changes, and the default path without a mounted-control consumer tracks no nodes.

The HHPI consumer compares the acknowledged object with the current accepted conversation node, then measures the actual row inside the official viewport. It publishes the greatest visible original readable event position only while the occurrence is ready, focused, visible and not busy. Ordinary DSH uses the committed Session event sequence and time; HHPI additionally requires the exact accepted Pane version and its original epoch. This bridge neither scrolls nor loads history, and layout acknowledgement alone does not claim browser paint or visibility.

The installed API remains optional, with no new dependency or persistence format. Contract tests exercise the real ChatNodeSeat and ChatSnapshotBuilder, same-key replacements, multiple seats, disposal and unchanged parent render count. Main-repository tests cover the actual SessionOccurrence lifecycle, the source epoch boundary, multiple visible rows, focus without a body, late mounting, busy readers and handoff cleanup. The release source offer includes this decision, the local upstream PR draft, the consolidated patch and the corresponding package source.

An update checkpoint has a separate failure path: `preparePageCommit()` only flushes pending scroll samples, so an unchanged reader may never save its current position. The optional `readingCheckpoint: 1` / `checkpointReading()` contract invokes the official reader to sample and save even without pending scroll events. It requires an initialized, measurable, stable reader and a real anchor when not following the tail. The memory provider's save failure propagates; existing saved positions do not stand in for current sampling.
