# Current-authority checkpoint and atomic byte publication

HHPI saves source files through a real source-local filesystem. The authenticated account may lose its grant while a replacement file is being staged. Checking authorization only before `writeText` starts or after it finishes cannot prevent that publication.

The DSH filesystem contract gains an optional sixth `writeText` parameter, `beforeCommit?: () => void | Promise<void>`, after the existing sandbox policy argument. LocalFileSystem invokes it inside the existing target lock after staging, fsync and permission preparation, immediately before the final cancellation check and native publication. An opted-in guarded write also rechecks its existing version/create guard after staging. A checkpoint rejection removes private staging and propagates the same error. SandboxedFileSystem forwards the checkpoint after its existing policy fence. Calls that omit it keep the existing path.

HHPI supplies a checkpoint that checks the source baseline, canonical workspace path, current session grant, and request/owner cancellation. The callback is a production API, independent of filesystem test hooks. Both POSIX publication and Windows DACL copying plus protected `ReplaceFileW` use the existing implementation. No client may supply an account, filesystem root, permission mode, or callback.

This narrows the read/check/write interval and serializes this provider's mutations. It does not provide atomic compare-and-swap against arbitrary external processes. The opaque stat version and existing guarded-create hard link remain the freshness mechanisms; no content hash is added. Disabling the HHPI integration leaves ordinary DSH callers unchanged.

Source packages affected are `@deepseek-ai/dsh-fs`, `@deepseek-ai/dsh-fs-local`, and `@deepseek-ai/dsh-fs-sandbox`, based on the pinned `0.2.2-rc.1` source. The extension source, package archive and provenance are maintained with the other approved DSH extensions. The focused source-plane tests cover deferral, refusal cleanup/error identity, staging-time external edit, concurrent creation, cancellation, sandbox refusal/forwarding, and the Windows native boundary call order. Actual native Windows acceptance remains a separate platform check.

File upload also needs exact byte publication. The official filesystem exposed byte reads but only text writes; decoding an upload as UTF-8 would corrupt arbitrary binary files, and an HHPI-owned replacement implementation would duplicate atomicity and Windows access-control handling. `FileSystem.writeBytes(target, content: Uint8Array, expected?, signal?, sandboxPolicy?, beforeCommit?)` therefore returns `FsByteWriteOutcome`, containing only `operation` and `version`. The caller retains the input buffer unchanged until the operation settles. Providers without a byte writer explicitly reject; they never decode or delegate to text writes.

LocalFileSystem uses the same per-target lock and private publication helper for text and bytes. Text retains its previous bounded contextual diff; bytes have no text diff. Both use the existing private staging, fsync, mode preservation, guarded-create link, Windows DACL/ReplaceFile implementation and optional checkpoint. SandboxedFileSystem applies its existing policy fence before delegating byte publication. This adds no new file transport or permission mode, and does not alter SSH provider behavior or a Session format.

The byte extension is covered by exact non-UTF-8/zero-byte/subarray publication, empty replacement, version/create guards, cancellation, checkpoint refusal/cleanup, mixed text/byte concurrency, POSIX permissions, explicit Windows syscall fixtures and sandbox denials. A real app/Loader fixture mounts the source filesystem and an injected consumer, then verifies its binary output without Agent services. Tests and declarations run against the prepared pinned source; development installation and native Windows acceptance are separate steps.
