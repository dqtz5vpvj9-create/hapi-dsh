# 冷启动与内存排查，2026-10-23

本轮已部署首屏分阶段加载、WebSocket 压缩、按需挂载源会话、小型首屏缓存和版本化静态资源缓存。生产无降速导航的正文约 2.06 秒；模拟 150ms 延迟、1.6Mbps 下行时仍需 15.44 秒。因此不能宣布弱网首次打开已达到 HAPI 的体验要求。

本文前半部分是上午发布检查点。后续滚动与大快照调查见文末；持续增长的生产会话在后续弱网样本中已超过上述等待时间。

## 开销来源与修复

1. **与阅读无关的插件阻塞首屏。** 修改前一次无缓存导航传输约 6.33MB HTTP 数据；账户设置包单独 gzip 后约 2.47MB。通过公开 index injection 组合初始清单，账户、插件管理、计划任务等在真实会话就绪后由官方 `ClientEntries.sync` 恢复。依赖闭包优先；显式打开相关面板也会触发。完整插件失败清单为空才标记完成。每个模块保留自己的官方资源 URL，避免一次 HAPI 更新让整个组合包失效。
2. **全部会话提前挂载，挤占 Host 内存和打开路径。** 排查确认过 Host 堆耗尽和自动重启，单次打开曾等 88.5 秒。目录现在只加载源摘要，打开时才挂载对应历史。未打开源的普通活动不再创建显示 Agent 和历史 journal；挂载期间的增量、删除和身份变化仍有覆盖。再次打开已有会话只确认身份和刷新设置，不再等待整份历史重新协调。近期列表统一呈现未挂载摘要与已有显示会话。
3. **读取完整缓存后再截断。** 新增独立的最多 200 条源记录首屏缓存，避免打开时解析整个归档。没有缓存时先读一页并验证源 epoch，完整性保持为未完成，较早内容仍走后台协调和官方分页。官方初始 follow 最多取 20 条消息；连续 seq、hasMore、上一页和后续实时事件保留。当前及上一轮内容在首帧后按既有两页预算补充。
4. **状态变化重复持久化整份通知。** 现将完整 status 域与 notices 域分别发布，旧记录仍可回放，最终公开投影保持完整。240KB 通知随 100 次状态变化造成约 24MB 重复记录的用例，新增日志现小于 500KB。官方线上投影仍可能重复发送 notices，尚未实现增量 wire 协议。
5. **控制流与首屏快照体积过大。** 通过公开 Connection socket factory 和 WebServer upgrade 路由给官方流加入压缩载体；保留 Host/Origin、凭据、逐调用授权、顺序、二进制、实际浏览器心跳、取消及重连。上游只固定连接同一 Host，慢接收端施加背压。列表省略重复的 turnOutline 提示，但 canonical/control/follow 投影仍完整。HTTP gzip 使用官方 profile 的 level 5 配置。
6. **刷新重新下载固定入口和 vendor。** 官方静态 fallback 没有缓存头，重复导航仍传输约 0.5MB 入口脚本和样式。通过公开精确路由只为 pinned Web frontend 已带版本名的 JS/CSS 添加 immutable 缓存；文件内容不变，HTML 认证、可变文件和 RPC 保持原处理。生产二次导航中四个 shell 资源传输字节均为 0，总 HTTP 从约 567KB 降到 53KB。

这些均为本仓库的插件组合和适配，没有修改 DSH 源码，也没有替换官方 Conversation。

最终弱网首屏传输约 2.37MB HTTP，源解析请求约 324ms，再次导航约 217ms。工作区在 12.41 秒才出现，随后 3.04 秒正文出现，首屏资源下载仍占主要等待。两个导航合计 WebSocket **解码**约 906KB，最大单帧约 404KB；这不是线上压缩后的字节数。压缩协商成功，没有 WebSocket 错误或浏览器脚本异常。

最终无降速首屏仍有 276ms、252ms 的主线程长任务。不能把没有再发生整页卡死写成没有长任务。CDP 整形不是用户真实线路；正文必须位于可见 pane 的实际滚动视口内，不能仅因隐藏节点已有文字就判就绪。

## 后续调查：资源、历史记录与实时投影分别计量

后续客户端拆出原生历史、会话工具和管理面板三个包内 chunk，沿用官方 `require.async()`；主包启用标识符压缩。主包在该检查点约 1.28MB raw / 375KB gzip。可选插件图与无关 Host 初始化等待读者操作的空闲窗口，正文初次出现后的生产触摸样本最大帧间隔从 633ms 降至 183ms；这是两个持续变化的线上样本，不能视为固定输入的因果基准。正在进行的同步插件工厂仍无法被中断。

相同 150ms / 1.6Mbps 整形下，后续生产样本的首次工作区、输入框、正文分别为 12.36s、13.21s、22.31s；带浏览器缓存再次导航正文仍为 11.12s。首次 HTTP 编码传输约 2.38MB，首次 follow 快照约 2.73MB 解码数据。另一组无降速诊断中，首屏 records 为 2.81MB / 765 条，远大于约 98KB 的当前投影。旧探针把 `plugin:` 类型归为 other，该组 other 为 2.47MB / 679 条；新探针按类型拆分，并只记录允许列出的字段字节与变化次数，不保存内容。

这说明等待至少包含两部分：下载启动资源，以及传输、解析首屏完整事件范围。输入框先出现并不能证明历史打开已经快；局部滚动改善也不能抵消 22 秒的冷导航。

修正分类后的生产采样进一步确认：首屏 1,078 条记录占 4,004,262 字节，其中 985 条插件记录占 3,666,318 字节。951 条旧 status 占 3,629,200 字节；execution 实际变了 949 次，而 resolvedRequests 只变了一次却重复占了 2,252,919 字节，delivery 只变了一次却重复占了 294,810 字节。这直接支持按域分离发布，而非猜测正文或工具输出是唯一大头。本次无降速正文 2.904s、输入框 2.320s，最长主线程任务 335ms，仍未解决首开长任务。

新增状态分域将 execution 与 session-state、notices 分开写入，均为完整域值，旧 state/status/notices 记录仍可重放。另用官方 ProjectionDefinition.wire 明确省略仅 Host 使用的 execution.sequence；Host 状态和原始事件保留该字段，客户端仍由官方 asOfSeq 排序。真实官方 SessionProjectionRegistry 的合成协议基准中，100 次仅 sequence 更新以前产生 100 次、3,798,594 字节的投影 JSON；新 view 为 0 次、0 字节，原始 execution 事件仍为 100 条。执行状态、turnId、等待原因、队列、审批和通知变化继续发布完整值。这是投影 payload 的结果，不是整体网络压缩比，也不意味着旧历史已经变小。

已有日志的瘦身受当前公开接口约束：官方 `@deepseek-ai/dsh-api-session-controller` 0.2.1-rc.2 的 `lib/types/types.d.ts:467–486` 只提供消息数和 turn 窗口，page 另有 throughSeq/beforeSeq；没有记录类型过滤、插件排除或字节/记录数上限。`lib/index.js:1717–1745` 只对 append-origin 正文计数，返回连续事件范围。因此夹在 20 条正文之间的大量历史插件记录仍随页传输。缩小消息数量不能可靠限制一个长 turn 中的插件数量；本轮没有删改原日志或私自过滤协议。
