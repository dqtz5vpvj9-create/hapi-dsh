## 最主要的失误

### 1. profile 成了记录系统，没有成为调度控制

我建了计时、DAG 和证据表，却没有导入已有 token 遥测，也没有根据持续消耗、未完成用户路径和重复失败调整工作。报告已经给出 21 组重复验证提示，执行仍在继续展开。既有文档要求比较返工与成本、没有新风险就停止扩测，问题主要是没有落实，而不是缺少另一套平台。

每条命令有超时不等于任务有预算：大量几十秒命令仍可以组成数小时调查。不同版本、不同标签还会重新获得一份局部预算。需要约束的是一条问题线从发现到交付的总成本。

### 2. 按模块并发完成，实际用户路径过晚贯通

文件功能已有源契约、组件与类型证据，但到约第 8 小时真实点击“Project files”时，仍连续发现：独立 Pane 排除 source provider、重复注册 mountedChatConsumer、四个直接调用 workspaceFiles 的 UI consumer 未走源路由。这些是接入断链，应该在最早的薄切片实开阶段暴露。

先把大量叶子节点标成 done，再由 root 集中接线、复测和部署，制造了集成尾部。最后的 52 个 done 与 64 条 user-workflow unknown 正好暴露这种错位。真实目录和 README 正文已在中断前打开，但这不补齐其他路径，也不应继续用低层测试数量表示完成。

### 3. RSI 对照扩张成另一项高消耗工程

同一候选进行了三版真实对照：13.21、12.01 和 30.00 分钟，合计 55.22 分钟，最终全部 incomplete，未晋升。最终版 12 个已完成 worker 产生 402 批命令，报告输入 19,308,405 tokens（其中缓存 17,940,736）、输出 83,251；超时 worker 消耗未知，不能记零。

保留失败结果是正确的，但开跑前没有用最小真实样本确认整个执行器和检查器可用。之后连续扩到下一版，把“验证 harness 是否改善”变成了成本显著的附加项目。最终有效候选结果仍未达到必要检查。用户要求 RSI 闭环，并不要求无限增加试验；一次有据的拒绝即可闭环。

### 4. 主代理成为昂贵且冗长的协调与集成中心

主代理 1,638 次响应平均带入约 158,391 输入 tokens。26 次压缩、312 次消息以及持续分阶段交接意味着大量上下文被反复携带。缓存减少部分计费工作，但不等于免费，也不能推断不占 Pro 周额度。

子代理采用用户指定的 GPT-6.1-Sol/xhigh，不应把问题归咎于这一要求。问题是任务切分后仍把大量实现、环境判断和接线留在主代理，形成“子代理局部完成 → root 重新理解 → 集成失败 → 再委派”的循环。没有单代理基线，不能声称本轮并发提速。

### 5. 环境准备、性能深挖和发布重组缺少整条问题线的停损

I6 记录 132 条非任务 span，其中 56 条 failed/timeout/cancelled，SDK 已推进到第 9 套候选准备；每轮可能有必要修改，但没有对总投入和新信息增量作及时裁决。真实手机准备到中断时仍未进入正式 V1/V2；Windows 退出恢复检查又在额度耗尽时留下离线 Runner。

故障检查本身必要，80ms 门槛、认证和执行归属也不应降低。错误是让关键路径不断串行膨胀，并允许会改变服务状态的演练依赖后续 Agent 额度才能收尾。演练应该在同一有界脚本内自带恢复，而不是靠下一轮对话来恢复服务。

## 下一轮应直接采用的执行调整

后续用户确认先落实“减少重复验证、按完整用户路径交付”，具体实现见[执行规则](development-profile-rsi.md#减少重复验证与完整路径交付)。下文是复盘时提出的建议，不作为新增预算门槛。减少并发并不保证减少总 token，用量缺失或过期也不阻止工作。

这些是基于本轮证据的执行修正，不推算 Pro 周额度；当前修复与复用入口见 [开发经验](development-practices.md)，产品实施仍暂停。

1. **先做能实际走通的用户路径，再扩模块。** 每个切片先实开一次入口→源操作→结果→返回。目录/编辑器/终端等不能只用自己的 fixture 证明完成。实现与该路径集成尽量由同一个子代理负责。
2. **限制同时在做的交付切片。** 先用两个实现槽加主代理集成；有真正独立工作再用第三槽，不为填满槽位拆任务。root 不重读子代理已经给出准确结论的全部材料，只检查契约、diff 和缺失证据。
3. **按新证据改变下一步。** 相同输入连续失败后先诊断；下一次执行须能验证新假设，不能靠反复构建期待通过。未知范围和已确认缺陷仍保留，按完整路径优先推进，不增加任意 token 或时间准入门槛。
4. **复用验证，失败按原因改变方法。** 对同一代码和环境保留已有结果；一次针对性验证加一次真实路径检查。只有代码变化、新失败或明确未覆盖风险才再跑。两次同类失败后必须换成有因果证据的诊断，不继续“再构建看看”。全量发布门禁保持。
5. **观测真实开发，取消额外 RSI 试验。** 用现有导入入口按响应去重记录主、子代理用量；CLI 和库均停止实验启动。历史负结果保留，改进落实到实际脚本与交付路径。
6. **改变进度单位。** 每轮报告新增打通的用户路径、剩余阻断和本轮用量，不以测试数、文档数、节点数或代理数量代替成果。同步更新已有证据，避免用户路径全 unknown 而节点大量 done。
7. **故障演练自行收尾。** 在一个有限执行单元内完成故障注入、观察和恢复；异常/额度退出时仍能恢复既有服务。没有可靠恢复安排前不做有副作用的演练。

结论：这次不是“只差再跑一些测试”。我把范围展开、模块进度和验证活动当成了推进，却没有及时用可用用户路径与实际成本检验它们。应先缩短从修改到真实结果的反馈距离，并限制调查与 RSI 的总投入。
