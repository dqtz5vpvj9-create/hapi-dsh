**目标：HHPI 成为不包含 HAPI 兼容来源的 DSH 远程编程工作台。** 本机 DSH 使用官方能力，远端 DSH 使用官方 federation，Codex 使用 HHPI 直连原生端。HAPI 只作为产品经验与可复用代码的来源；交付后的 HHPI 不连接 HAPI Hub/Runner，不接受 HAPI 来源配置，不注册 HAPI 来源入口，也不保留按开关启用的兼容后端。

这次改变的是最终架构和退出条件：先把文件、终端、通知及其他日常工作流接到独立服务，完成旧数据和执行归属的转移，再删除旧路径。仅隐藏菜单、默认关闭配置或声称“不依赖 HAPI”都不算完成。

本方案保持 HHPI v1 的方法、字段、错误码和原生执行归属，不迁移到 AHP，不引入外部 AHP Host，不批量重命名包或会话 ID。用户已授权实施及发布；原设计阶段的“只写文档”限制不再适用于当前执行。旧 AGENTS/README 中的“可选 HAPI 来源”已被用户决定取代，不能再以旧定位保留兼容路径。

## 0. 修复后用户应得到什么

**交付目标：用户能在同一个 DSH Web 工作区里，用桌面和手机完成跨机器编程任务，从找回或创建会话、输入与审批，到查看产物、编辑源文件、使用终端，再到离开后收到提醒并返回继续；整个日常流程不需要 HAPI 服务，也不存在可切回的 HAPI 兼容来源。** 保留真实源身份和执行归属，操作异常时保护工作内容，并有可继续的恢复路径。

这句话描述的是实施和验收完成后的产品状态，不是当前状态。完成判断取决于下文的用户结果和证据，不用代码量、测试数量或主观百分比代替。任一必交付流程尚未接通，或必须的实际环境验收未执行，整体交付仍未完成；已验证的独立修复按现有规则及时上线。

| 原计划的问题 | 本次确定的交付责任 | 归属与完成证据 |
| --- | --- | --- |
| 文件编辑被写成“等原生 API 有条件写再开放” | M4 接通直连来源的文件工作台与保存，复用已有编辑、草稿和冲突恢复流程 | 源机器文件服务；实际编辑、保存、源端读回、冲突及返回原草稿 |

上述功能实现仍属本次方案；手机专项验收按最新用户指令停止。还要逐项覆盖第 6 节的 A1–P4；不能因为用户只追问这四项，就忽略分享、更新、设置、子任务和其他二级界面的完整流程。

### 本次交付的适用对象

最终只保留本机 DSH、远端 DSH federation、HHPI 直连 Codex 三条接入路径。HAPI 来源、通过 HAPI owner 控制的 DSH 来源及其运行时兼容注册全部退出；旧数据按第 4.4 节迁移，不能通过删除用户数据来完成代码清理。直连 Codex 的文件和终端由该机器上随 HHPI 分发的工作区服务提供，不要求安装 HAPI，也不把浏览器展示转成一个新的 DSH 执行 Agent。合法只读授权仍只读；不能通过把正常可写来源改成“只读”来宣称接入完成。

桌面浏览器和手机 Web 是交付面。手机首先覆盖用户实际使用的 Android 浏览器与中文输入法；iOS 若列入发布支持声明，也必须有对应真机证据，不能用 Android 或桌面模拟代替。可选语音、额外通知渠道、原生手机 App、商店发布、Host 重启后继续存活的终端进程，以及无限文件大小不因本方案自动新增为产品承诺；仍属于 HHPI 的相关入口保持正确；仅服务于 HAPI Hub/Companion 的专属入口随来源一起删除，具体边界见第 4.3 节。

### “删除 HAPI 兼容来源”的关闭条件

| 检查层 | 最终必须成立 |
| --- | --- |
| 安装与运行 | 全新安装无需 HAPI URL、令牌、数据库或进程；旧安装转移后同样能独立工作 |
| 来源与控制 | 来源列表和新建菜单只有本次保留的三条路径；没有 HAPI owner 控制桥、Hub 会话代理或隐式回退 |
| 文件与应用服务 | 文件保存、附件、PTY、通知、已读、分享和更新都走已授权的独立服务 |
| 代码与产物 | HAPI 客户端、适配器、注册、专属 UI、依赖与打包入口退出生产代码和发布产物；关闭开关或 tree-shaking 不是删除 |
| 旧工作 | 可映射的原会话、草稿、附件、布局和阅读位置得到迁移；无法精确映射的内容保留可访问的离线恢复包并逐项说明，不能丢弃或伪造原生历史 |
| 执行所有权 | 不创建第二个写入者，不自动重发旧队列，不强停仍由旧 owner 持有的任务；有未决执行归属时，该来源切换尚未完成 |
| 协议 | HHPI v1 方法和字段仍兼容；`legacyHapi` 固定为 `false`，不再启用来源；`legacyOrigin` 仅保留可选 wire 定义，不被用于联系 HAPI |

删除 HHPI 内的来源接入，不等于卸载用户另外运行的 HAPI 应用，也不授权清理其数据库、凭据或进程。验收在没有 HAPI 的隔离环境和已经转移的 HHPI 安装上完成，不通过停掉无关服务证明独立性。

### 第六次修订：缩短反馈，按依赖并发实现

后续实施同时遵守[交付方法第 8–10 节](hhpi-delivery-method.md)：子代理交付完整功能及局部验证，主代理负责公共契约、持续集成和统一发布。按一个主代理加最多三个 Codex 子代理起步，再根据实际依赖和名额调整；不以固定代理数量或测试工时比例判断效率。

开发时按明确文件或行为选测，集中执行每个可发布批次的完整检查，避免 `check → test:release → deploy` 重复验证同一代码。共享文件只有一个写入负责人，检查时保持相关代码稳定；没有新修改、失败或具体未决风险时停止扩大验证。真实 UI、真机、认证、原生执行和发布要求保持，不能以提速减少产品范围。

新增六项来源记录了测试选择的局限、原生 Codex 并发可能变慢、按依赖划分任务的加速结果，以及隔离和集成的代价。研究结果与本项目执行安排分别陈述；实际效果看可用版本交付时间、重复验证、等待及集成返工，本轮未启动实施代理或产品测试。

### 第七次修订：按细粒度 DAG 动态派发

| 实现与审查共享不完整的清单 | 独立审阅首轮只从原始目标、真实材料和原生基线推导行为，保存后才看实现清单 | 交付方法第 3 节；范围差集和未验证完成声明均须处置，角色数量不作证据 |
| profile 只有记录，没有改善实际交付 | 用实际路径、返工、重复确定性工作和新发现判断流程效果；不新增模型对照任务 | S1 保留用户判据；S2 已取消，历史负结果保留 |

研究依据、可支持的结论和适用限制见[交付方法第 11 节](hhpi-delivery-method.md#11-本次失败研究如何改变执行)。本次补充的是可执行责任，不宣称这些方法已经使 HHPI 无遗漏。无需用户补齐每个常识性行为或逐项重新批准普通修复。

## 1. 先回到 HAPI-DSH / HHPI 的 motivation

当前 [AGENTS.md](../AGENTS.md#L3)、[README](../README.md#L3)、[交接目标](../HANDOFF.md#L3)和[远程接入设计](hhpi-remote-access-design.md#L5)的共同动机仍保留，但其中“可选 HAPI 来源”的安排由本计划明确取代：让用户在一个 DSH Web 工作区里，访问不同机器上原本就在运行的 Agent，并获得完整的工作体验。

| 要解决的问题 | 产品必须提供什么 | 架构上的含义 |
| --- | --- | --- |
| 工作散在不同机器、引擎和已有会话里 | 一个侧边栏、一个工作区；找回原会话，接着做 | 原生 thread/session 身份不变；不为展示重建执行 Agent |
| HAPI 已有实用的远程编程工作流，但目标前端是 DSH Web | 保留文件、结果、计划、审批、历史、并行工作等实际用途 | 学习 HAPI 的行为与经验，使用 DSH Conversation、编辑器、读者和插件承载 |
| 单纯显示聊天文字无法完成编程任务 | 输入上下文、查看过程、使用产物、处理问题、采取下一步 | 能力必须接通入口、执行、结果、恢复与返回，不以转发 API 为完成标准 |
| 远程环境会断线，长会话和多 Pane 会持续增长 | 离开后能继续，历史连续且位置稳定，操作不重复 | 会话事实、操作身份、阅读窗口和视图生命周期分别管理 |

HAPI 从运行时来源中完全退出；已有实用工作流由 DSH 原生能力或 HHPI 自有服务承担。复用其代码必须解除 Hub/Runner、消息投影及凭据依赖，保留许可证和来源记录。另一方面，语音、原生手机 App、商店发布等功能不能仅因 HAPI 有实现就自动成为 HHPI 当前必做项。

因此，“做成完整 HAPI 超集”和“只支持源端声明的 send/steer”都不足以描述本项目。正确的要求是：**对产品已经承诺接入的引擎，把其适用的编程能力在 DSH 工作区内接完整；源端确实不支持的能力如实表达。不能用一份过窄的声明替尚未完成的接入免责。**

## 3. 当前真正需要处理的架构问题

### 3.1 接入已经通用，应用能力仍分成两条路

`hhpi/*` 已有目录、读取、操作、资源、创建及 native carrier。可是主界面 Codex 新建表单调用 `HapiRemoteApi.createSession`，其他源创建表单调用 `createSourceSession`；`RemoteSessions.create`仍委派普通 DSH create。没有发现这条主表单调用 `hhpi/create`。这是一处具体的“后端具备、入口没走到”的断点。

文件和终端也有同样的分界：`NativeAwareWorkspaceFiles`、旧源终端通过 `legacyWorkbenchSource`进入 HAPI Runner；这个函数对 `hhpi:`明确拒绝，避免误读主 Host 的文件。它是正确的安全边界，但也说明直连来源尚未获得同等的文件工作流。`capabilities.files=true`在当前上下文是附件输入能力，不能拿来宣称完整远程文件树、编辑器和终端已经可用。

证据：[新建入口](../src/client/ui.tsx#L568)、[HAPI 新建调用](../src/client/new-session.tsx#L172)、[直连 facade](../src/client/remote-sessions.ts#L657)、[工作区文件](../src/hapi/workspace-files.ts#L157)、[源作用域保护](../src/shared/source-access.ts#L8)。

### 3.2 成熟的操作对账没有覆盖所有用户入口

`remote-codex-actions.tsx`把请求保存在 React state，`remote-input-triggers.ts`把未决命令保存在 Map，`CodexSettingsController`保存在 WeakMap 下的内存对象。它们在同一次挂载或运行期间能查询原回执，但刷新之后无法从这些对象恢复请求身份。源端 ReceiptLedger 可以阻止同一个 ID 重复执行，却不能替浏览器记住已经丢掉的 ID。

计划动作做得更完整：它先保存请求，再调用 nativeCall；但使用独立的 `hhpi-plan-action:${sessionId}:${planId}` localStorage 记录，而主 HHPI 操作采用 authenticated storage scope 和 IndexedDB 事务。计划记录不在 `clearSourceStorage`当前清理的 reading/outbox 前缀内，也没有获得主事务路径的多标签页认领。这里确认的是所有权和契约不一致，不是已经复现了跨账号泄露或重复实施。

证据：[更多动作](../src/client/remote-codex-actions.tsx#L7)、[命令 pending](../src/client/remote-input-triggers.ts#L22)、[设置 pending](../src/client/remote-codex-controls.tsx#L22)、[计划记录](../src/client/source-plan.tsx#L17)、[清理范围](../src/client/remote-storage.ts#L6)。

### 3.3 原生方法可调用，不等于有可完成的用户动作

例如 `/fork`和更多菜单的分支动作会发出原生请求，但前者仅以 CommandClaim 文案结算，后者只提示“新会话会出现在列表中”，没有把原生返回的目标接入打开/定位流程。普通 `RemoteSessions.fork`又对 `hhpi:`拒绝。三个入口呈现三种完成方式。

模型和权限控件根据 `capabilities.steer`判定可写，把“线程已加载、允许 steer”同时用作“设置可编辑”的条件；这不是设置能力的独立契约。原生方法表里已有队列、Goal、历史搜索、技能/插件等不同类别，不能仅凭静态注册表就认定全部实际可用，也不能只提供一个原始 RPC 面板代替它们的工作流。

证据：[fork 结果](../src/client/remote-codex-actions.tsx#L47)、[facade fork](../src/client/remote-sessions.ts#L662)、[设置准入](../src/client/remote-codex-controls.tsx#L46)、[原生方法目录](../src/remote/codex-methods.ts#L1)。

### 3.4 过程已经收拢，用户决策仍有原始数据直接落在主界面

普通审批卡默认展示 method 和 `JSON.stringify(request.params)`。权限请求默认打印 permissions JSON；`item/tool/call`进入 SourceNativeQuestion 后，只有“需要对应的原生能力处理器”的提示，不提供实际处理器。对最后一种请求，产品必须提供已注册的能力处理器或诚实保留待处理状态，不能制造自动批准或假结果。

这与“继续把所有过程折叠掉”是不同的问题。审批的命令、修改范围、对象、理由与可选决定必须让人能理解；原始参数可以放进详情。

证据：[普通审批](../src/client/remote-controls.tsx#L90)、[问题和权限](../src/client/remote-native-question.tsx#L38)。

### 3.5 注意力、安装与更新仍被 HAPI 能力门控

源通知与 read-sync 在 `legacyHapi`为 true 时才安装。通知组件里同时包含 Push、安装和更新 UI，因此 HHPI-only 不会获得这条安装路径。它不等于普通 DSH 没有任何通知，也不等于应用没有 Service Worker；准确的缺口是这套源通知/安装/更新与已读同步尚未变成适用于 HHPI-only 的完整流程。

前台可用现有目录、metadata 和已接受的事件判断活动与待处理项；浏览器关闭后的 Push、跨设备已读则需要真实后台能力，不能只在前台调用 Notification API 就算接入。

证据：[安装门控](../src/client/index.ts#L340)、[通知安装器](../src/client/source-notifications/index.tsx#L12)、[通知桥](../src/workspace/notifications.ts#L13)、[HAPI read-sync](../src/workspace/read-sync.ts#L9)。

### 3.6 工作台服务被错误地等同于 Agent 原生能力

原计划把文件保存、用户终端和后台提醒都写成对源 Agent 原生接口的依赖，混淆了三种能力。模型、轮次、队列、Goal 和审批由 Agent 原生所有者决定；文件和用户终端属于授权的源机器执行环境；后台通知、已读和安装更新属于应用服务。DSH 插件架构能够承载后两类服务，不需要让 Codex app-server 额外实现它们。

这也不是把 `hhpi:` 改成普通 sessionId 就能解决。当前 DSH 终端从 `Agent.ctx` 取得 subprocess、workingDirectory、sandboxPolicy，并随 owner 生命周期清理；文件服务从授权 Session 的真实上下文解析目录。需要显式绑定源机器工作区和资源所有者，不能复用中央 Host 的 ctx，也不能为了看文件新建执行 Agent。

源码核对以当前安装的 `0.2.2-rc.1` 产物为准；相邻 `dsh-ext` 源码工作树的包版本仍写 `0.2.1-rc.3`，仅辅助理解机制，不作为当前已安装版本的证明。当前发现属于接入和服务组合缺口，没有在本轮执行 GUI 复现。

## 4. 按四项责任调整模块

保持现有模块的有效机制，新增的通用契约先放在 HHPI 自己的代码中。以下名称表示职责建议，不要求建立新的进程或一个包揽所有状态的总管理器。

| 责任 | 当前可复用 | 应调整的内容 | 明确不承担 |
| --- | --- | --- | --- |
| 源能力与资源接入 | SourceAdapter、CodexAccessBridge、DSH federation、现有文件/终端的可复用逻辑 | 删除 HAPI provider 后分开路由 Agent 原生控制与源机器工作区服务；为直连来源绑定文件、保存、PTY 和授权上下文 | 不在中央显示 Host 执行远端任务；不放宽 ACL；不为展示创建执行 Agent |
| 会话事实与操作状态 | SourceEventIndex、CodexObservation、RemoteSessionState、RemoteOutbox、事务与 receipt | 给 nativeCall 用户动作接入一致的作用域、持久意图和对账；保留各动作独立的完成条件 | 不把 RPC 接受等同完成；不以 metadata 相等证明某个操作已经确认 |
| 应用工作流与持久状态 | WorkspaceController、SessionBinding、reading occurrence、草稿、导航及通知/已读基础 | 统一入口路由；完成创建、分支、文件、终端、后台通知、跨设备已读与更新恢复 | 不以当前焦点代替原 binding；不把关闭视图当停止执行；不依赖浏览器活着才能发现任务完成 |
| 呈现与交互 | 官方 Conversation、输入、过程、媒体、计划、Files/Terminal 及 slots | 使用语义请求卡、源动作状态和正确的数据 provider；核查二级界面 | 不再写通用聊天 renderer；不通过 DOM 模拟点击或修改编译产物接入 |

一个有副作用的用户动作应经过：**当前 SessionBinding → 正确能力提供方及授权 → 该动作需要的提交记录 → 执行 → 原回执/真实结果 → 返回与恢复。** 普通读取不写操作日志；PTY 按键沿用 DSH 有序输入和确认，不进入可自动重发的业务 outbox。

### 4.1 三条服务路径与不变的 HHPI 协议

| 用户操作 | 服务路径 | 身份和所有权 |
| --- | --- | --- |
| 发送、插话、审批、分支、模型与原生队列 | 官方 DSH federation，或现有 HHPI/native carrier → 原 Agent | 保留 thread/turn/request/operation；由原执行所有者裁决 |
| 文件树、编辑保存、产物、用户终端 | 官方 DSH 文件/Terminal UI 与 slots → 工作区 provider → 授权源机器的 FS/PTY | 账号、source、machine、原 session 与 workspace 绑定；资源归源端 owner，视图只有租约 |
| 后台通知、跨设备已读、安装更新 | 应用 shell → 独立应用服务；Host 订阅已有源事件 → 推送 provider → service worker | 账号、设备订阅和确切源事件/阅读位置；不依赖任一 Pane 挂载 |

HHPI v1 不新增方法、字段或错误码。优先复用 DSH 公开 Remote、provider、slots 和当前 HHPI 自有 Workbench 服务；需要新增的工作区保存或应用通知服务属于插件公开服务契约，必须在实现清单中写明，不能伪装成现有 HHPI 或 Codex 原生方法。注册新服务仍须使用既有 Typert/Gateway 认证与资源授权，不能开旁路执行端口。

对普通/远端 DSH 使用原工作区上下文；对仅有 Codex 的源机器，由随插件安装的源端服务持有明确的工作区上下文，接入同机 FS/subprocess provider。源未配置时在接入流程中完成配置并说明状态；缺少此服务是该来源接入未完成，不能长期改标为“Codex 不支持”。

### 4.4 一次性迁移：保留用户工作，退出旧 owner

迁移是本次交付任务，不是永久保留 HAPI provider 的理由。工具只处理明确选定的本地快照/导出和授权原生源；不安装在线 HAPI client，不在每次启动或打开 Pane 时扫描旧 Hub。最终产品只消费当前格式与有限的精确身份别名。工具与必要恢复材料独立交付，生产包不包含旧后端。

| 对象 | 处理办法 | 不能做的事 |
| --- | --- | --- |
| 会话身份与旧链接 | 从已有明确记录取得旧 hub/session/display 与真实 machine/source/native ID 的映射；核对原生源身份和当前账号授权，持久化本地别名，再重绑 Pane、历史链接、通知目标 | 按标题/cwd/时间猜会话；将旧 seq 当原生 turn；把别名当授权依据 |
| 活跃会话与写入 owner | 转移前停止旧入口接纳新提交，结算已提交操作与待审批；能原生交接的只按受支持契约交接，否则等原任务结束后再切换可写路径 | 自动启动替身 Agent、抢锁、杀 HAPI 进程、让两条路径同时写同一任务 |

| 布局、阅读与已读 | 转换 Pane、父子关系、置顶、草稿、阅读锚点和账号已读记录。锚点缺少精确映射时保留旧信息，落到明确的安全位置并说明 | 按展示编号猜定位；把打开列表/迁移缓存当已读；跨账号批量合并 |

| 通知与设备订阅 | 独立 Host 提供 VAPID/订阅管理；按实际 origin/key/账号条件重新绑定，保留用户通知选择。转移后新服务只对新事件通知 | 导出私钥到前端；迁移时批量重推旧完成；旧账号订阅收到新账号信息 |

每项迁移记录输入版本、身份映射、原内容/对象数量、成功项及未解决项；复用现有事务、主键和版本机制，不新加通用 hash 校验。重复执行恢复同一转换结果，不重复导入或发送。缺少映射的对象保留在可访问恢复包并给出具体原因；用户工作无法继续、附件缺失或活跃 owner 未退出时，不能将该来源标为转移完成。若旧安装包含仅经 HAPI 接入、当前没有原生适配器的其他引擎，列入明确的迁移未解决项，不能把其历史冒充 Codex/DSH，或把隐藏这些会话算成升级成功。

切换按已完成来源进行：备份旧配置与数据，先验证新路径读取和必要能力，再停止旧入口的新提交并完成上述转移，随后启用唯一新写入路径、删除旧注册。回退使用已有版本和数据备份；必须先核实新路径的提交结果与 writer 归属，不能覆盖新数据或同时重启两个写入者。保留旧构建仅用于既有发布回退，不作为新版本内常驻的兼容模式。

## 5. 九组交付任务：删除旧来源与补全工作流一起完成

每组按完整用户动作切片，统一执行[交付方法](hhpi-delivery-method.md)第 1–4 节：先核对必要行为及依据，实施后从原目标查漏，再按真实证据结算。适用的独立审阅、交接与未完成项不能因为代码任务已结束而省略。

### M0 · 完成 HAPI 来源退役

必交付 P0，贯穿 M1–M8；不是先删除功能再慢慢补回。

先建立 R1–R10 的导入、注册、配置、资源与存储去向清单。M1/M3 提供唯一原生任务入口，M4 迁出资源服务，M6 迁出应用服务；每个替代路径完成后，迁移对应数据并删除旧实现、专属测试及打包注册。新功能从开始就只接保留的三条路径，不再增加 HAPI 分支。

最终检查同时覆盖源码和产物：HapiClient、DshOwnerConnection、HAPI 观察代理和 Hub RPC 无生产可达引用；没有旧后端动态导入、配置开关、默认 token、兼容菜单或随包复制的旧源码。仍含 HAPI 字样的许可证、历史文档、稳定包名、惰性 wire 字段及独立迁移材料须逐项说明，不能用字符串计数冒充依赖审计。

在从未安装 HAPI 的环境完成新装和完整主流程，再用旧安装快照完成升级、断线、重启和原任务恢复。验收期间从服务注册与网络记录确认不存在 HAPI Hub API/Socket.IO 访问；仅把 HAPI 地址配成不可达而仍不断重试，不算独立运行。全部 R 项退出、新服务完整、迁移结果可用才关闭 M0。

### M1 · 建立来源能力与入口路由表

优先级 P0，作为后续功能接入的依赖。

增加 HHPI 内部的能力视图，只区分本机 DSH、官方 DSH federation 和 HHPI 直连 Codex。它组合已有 `SourceCatalog.sources`、SourceSession、nativeCapabilities、原生 metadata 和当前调用授权；分别表达能力是否存在、是否可操作、为什么暂不可操作。方法注册、原生在线、线程加载和用户有权限是四种不同事实。

视图覆盖 create、settings、fork、queue、goal、files、terminal、skills/plugins 和 attention 等产品能力，并标明提供方是 Agent、源机器还是应用服务，但**不向 HHPI v1 新增字段**。不要继续用 `files`推断文件工作台，用 `steer`推断设置能力，用 `legacyHapi`决定所有来源是否能安装应用。客户端的能力信息不能代替服务端每次授权。未配置、未接入、未授权、暂离线和上游确实不支持分别表达；“未接入”必须有对应实施项。

同时维护固定 native 方法到产品工作流的映射：已由官方 DSH 页面承载、需要源适配、尚缺用户流程、或有明确限制。保留现有完整 carrier；尚未做的 UI 记为“待接入”，不能改写成“源不支持”，也不为每个底层维护方法各造一个按钮。可信本机验证等既有安全限制继续单列。

入口先按当前 binding 找到对应 provider；菜单、`/`命令、计划卡、侧栏和官方消息动作共享同一个路由选择及业务处理器。普通 DSH 仍走官方路径；任何入口都不能回落到 HAPI 或寻找旧 Hub owner。缺少能力的入口给出合适去路，不落到主 Host 的默认能力。

模型、技能、插件等目录按 source/generation 共享并按需读取，不让每个 Pane 重复拉全量目录。能力发现不扫描 transcript，也不为了展示菜单启动或恢复执行。

主要调整：`remote-sessions.ts`、`composer-picker/*`、`remote-input-triggers.ts`、`native-action-api.ts`、`source-access.ts`及 provider 组合层。可新增小型的 source feature registry，不复制另一套会话引擎。

验收：同一工作区同时打开本机 DSH、远端 DSH、直连 Codex；HAPI 来源不出现在目录、新建、设置或延迟菜单中，旧入口只按已完成的本地映射定位原任务。每个入口选中正确来源；没有源权限的文件或设置调用明确拒绝，其他会话继续可用。

### M2 · 将原生用户写操作纳入持久意图与恢复

优先级 P0，先覆盖现有入口，不等新增功能。

复用 RemoteOperationLedger 的事务机制和 authenticated storage scope，为设置、分支、上下文整理、Review、计划动作及后续队列/Goal 提供按动作类型保存的最小请求。`/`命令和更多菜单不再各自创建一份易失的 pending；SourcePlanOperation 迁到同一作用域和认领机制。多 Pane、多个标签页和重载共用原 ID。先查询 nativeReceipt，只有现有契约明确证明未派发且允许时，才继续同一请求。

统一的是持久所有权、提交认领和回执查询，不是把所有动作塞进 send 的状态机。compact 的 RPC 接受后仍要等原生完成；分支接受后要解析目标；设置的当前值收敛与该操作的 receipt 分开；控制请求仍绑定原 turn/request。已经结束的目标不能替换成当前目标。

把账户切换、来源撤销和旧记录迁移一并覆盖。仅迁移身份、状态及必要的用户输入，不把令牌、完整配置或敏感原生响应普遍复制到恢复日志。缺少身份范围的旧计划记录不能自动派发；保留可确认归属的内容并提供明确恢复状态。

新建/分支的源端记录还要保留确切目标关联：已接受请求、得到的原线程身份和结果分别持久化，按同一操作 ID 查询/返回已有结果。只在确认尚未派发时允许第一次执行。源执行后、关联尚未落盘的崩溃窗口若无法从源事实精确恢复，保留待确认和用户可执行的查找/关联去路；不宣称全局 exactly-once，也不自动再创建。M3 的自动打开只使用已证实的关联。

文件保存沿用源版本、草稿和未知结果检查；终端输入沿用其附件序号与 ack。统一作用域和生命周期不等于统一重发策略；禁止把文件写或 PTY 输入塞进普通消息重试。

主要调整：`remote-operation-ledger.ts`、`remote-storage.ts`、`remote-codex-actions.tsx`、`remote-input-triggers.ts`、`remote-codex-controls.tsx`、`source-plan.tsx`及源端创建结果记录，复用源端 ReceiptLedger。

验收：请求已被源接受但回执丢失，分别关闭更多菜单、切 Pane、刷新、打开第二标签页。恢复只查询原请求；不会出现另一个 fork/计划执行；撤销来源后旧内容和旧回调不能重新派发。现有消息 onAccept、草稿与附件接纳继续保持。

### M3 · 接完整的新建、分支、设置及原生任务工作流

必交付 P0；创建和分支先做，队列、Goal、搜索及其他适用能力在后续切片完成，先后顺序不代表移出交付范围。

1. 新建选择器按真实来源显示机器、引擎与可创建能力。直连 Codex 进入已有 `hhpi/create`能力，不调用 HAPI 机器/创建表单；普通及远端 DSH 继续官方 create。创建返回确切 SourceSession 后 resolve/retain 并打开，在目标 ready 前保留创建结果与草稿。`hhpi/create`目前只有 sourceId、operationId、cwd，不能假装支持完整模型、权限和 worktree 启动字段；这些设置在新线程 ready 后按原生设置契约处理。
2. 分支按钮、`/fork`及适用的消息动作使用同一处理器。从原生响应取得确切 thread ID，再走已有 resolve 和工作区打开/定位，保留父 Pane。消息边界分支只有在能精确映射原生边界且源支持时开放，不能把展示 seq 当 turn ID。
3. 设置按独立原生能力展示模型、推理强度、权限、模式及服务级别，保留已报告值与“未报告”的区别。只读历史的可读性与消息提交能力继续分开；历史线程不能因未 loaded 就被界面误判成永久不支持设置。是否允许为一次显式设置恢复线程，仍按既有 writer ownership 和源端规则裁决。
4. 将 native queue、Goal、后台任务、历史搜索、技能/插件等列为具体能力接入项目，逐项提供有意义的入口和结果，而非通用 RPC 表单。先补源实际具备且属于日常编程的能力；源不提供的能力说明限制。已有父子目录投影保留，重点检查从工具详情打开子会话、继续和返回父任务。

每类原生处理器对照固定 app-server 版本的请求/响应契约实现；方法名和 read/write 注册表不证明参数映射正确。普通文本、原生结构化输入、附件 receipt 和原始 thread/turn/item 身份要分别保留语义。

这些接入项目至少包含以下用户行为；同一原生请求只保留一个业务处理器：

| 能力 | 复用的既有 native 方法类别 | 要接到的实际流程 |
| --- | --- | --- |
| 原生队列 | `thread/queue/list/add/update/delete/reorder/start` | 查看、编辑、取消、调整次序或开始；保留确切队列项 ID，源已开始执行时不能把旧草稿悄悄重新入队 |
| Goal 与后台工作 | `thread/goal/get/set/clear`、`thread/backgroundTerminals/*`等源实际声明的方法 | 查看当前目标、显式修改或清除，进入具体后台工作；不伪造源没有提供的暂停/恢复或完成状态 |
| 历史查找 | `thread/search`、`thread/searchOccurrences`及已支持的分页/定位 | 查询真实来源的历史，区分标题筛选和正文搜索；结果打开确切原会话/内容边界，返回时保留查询 |
| 技能与插件 | `skills/list`、`plugin/list/installed/read`等 | 源目录、候选、选择、正确原生输入和结果；仅把名称插进文本不能算完成。先核对编辑器公开的结构化提交契约，不用隐藏字符串约定补协议 |
| MCP/外部能力 | `mcpServerStatus/list`、资源读取和已有受支持授权入口 | 显示实际连接与授权状态，从错误回到正确来源的配置；需要可信本机 UI 的能力继续保持限制，不能以远程 carrier 绕过 |
| Review 与 compact | `review/start`、`thread/compact/start` | 显式开始，跟随原生进度与终态，结果可读；接口接受后不立即显示“已完成” |

当前恢复缺口：`hhpi/create`没有独立的创建 receipt 查询，native carrier 的结果正文也不保证跨源端重启持久保存。由 M2 补源端最小结果关联，并在现有响应/原生 receipt 路径能够表达的范围恢复，不新增 HHPI 方法。已记录结果必须恢复并打开；没有关联证据的崩溃窗口提供明确的待确认和人工选择已有目标路径，选择不能伪装成原回执。不能只留下“新会话会出现在列表中”的提示，也不能按标题猜目标后自动继续写入。

主要调整：`ui.tsx`的新建选择、`new-session.tsx`/`source-session.tsx`来源路由、`remote-sessions.ts` facade、`remote-codex-actions.tsx`、`remote-input-triggers.ts`及既有原生处理器。

验收：未配置 HAPI 的工作区从新建走到首次输入；分支后直接到新会话、返回父会话且草稿仍在；丢回执后不重复创建；在同一操作的菜单和命令入口之间切换，看到一致状态。

### M4 · 交付源文件编辑、产物与可靠终端

必交付 P0。文件保存与用户终端和目录、预览同属本组；不再只交付只读页面后等待 Codex 增加接口。

**M4a · 文件与产物路由。** 保留官方 Files、DocumentPreview、deliverables 与资源 provider；在 HHPI 自有组合层按完整来源选择实际机器服务。普通/远端 DSH 走其工作区文件服务，直连 Codex 走第 4.1 节的源工作区服务。原生 Codex 文件方法可作为已授权且语义匹配的读能力复用，但不作为编辑和 PTY 的唯一后端。两台机器的同名路径必须是不同资源，目录、符号链接与源撤销保护保留。

从聊天中的图片、生成文件、相对链接、搜索结果和 Diff 进入同一文件身份；能够看原件、下载、选区引用并返回原入口。引用只加入原草稿，不擅自发送；切 Pane 后迟到读取仍归原对象。媒体、PDF、音视频和其他已声明支持的格式要实际可读/可播放或提供原件；转换失败不能阻断下载。代码、表格、数学和图示保留原生渲染及失败退路，不能因为它们来自工具结果而折叠掉。

**M4b · 编辑与管理。** 复用 `SourceFileEdit`、`source-file-actions`、`native-document-journal`、现有 Workbench 保存与恢复界面，把 HAPI 专属身份换成明确的来源 provider。DSH 官方 workspace-files 仍只读，保存是自有工作区服务的显式动作。覆盖打开→编辑→保存→源端读回→继续编辑，以及创建、改名、移动、复制、删除、上传/下载等已有管理入口；多项操作按各自真实结果反馈。

保存继续携带读取基线和确切目标，由源机器服务检查当前版本及写权限；冲突时保留本地修改，允许查看差异、载入源版本或明确处理冲突。保存期间的新输入保持未保存状态；回执丢失先检查原操作与源版本，不能盲目重写。抽取并复用已有版本/观察与保存保护，不新增通用 hash 校验层。实施时核对既有保存服务的临界区和外部写入边界；普通“读后写”不能被声称为对任意外部进程原子 CAS。应由源服务完善必要的保存保护，不把这项实现责任推给 Codex API。

同一授权源文件共享已确认的源版本；各编辑视图保留自己的光标、选区和未提交修改。另一视图或外部程序修改时显示差异与冲突，不用较晚返回的读取覆盖脏稿。刷新、更新、失联和来源切换都覆盖草稿恢复。

**M4c · 可靠终端。** 复用 DSH `terminal-controller` 的 create/list/retain/attach/close、真 PTY、屏幕恢复、序号和 ack、慢消费者处理及客户端模型；第 4.2 节的上下文扩展解决 Codex-only 来源的资源 owner。工作目录、系统用户、沙箱权限与 lifetime 必须来自实际源机器；只持有工作区资源上下文，不创建新的执行 Agent，也不接管 Codex 自己拥有的工具进程。

关闭 Pane 只释放视图；隐藏标签按现有规则 retain，显式关闭终端才结束对应 PTY。断线不停止进程，重连恢复同一终端并忽略旧连接回调，未确认按键不得重放。保留官方单输入控制权规则，并在另一窗口接管时解释当前只读状态。手机控制键、粘贴、复制、resize、退出与返回都使用实际终端 UI 验证。保证范围是源 owner 存活期间的浏览器断线/刷新恢复；Host 或 owner 重启后如原进程已不存在，应明确显示终端结束，不能自动新开 shell 冒充恢复。

**M4d · 附件传输。** 保留选图后启动上传、上传内部先在本机准备图片的分层。普通文件使用源机器文件服务的二进制/流式能力，优先复用 DSH 公开传输；确需自有上传会话服务时，记录目标、进度、取消与返回的源文件身份，不向 HHPI v1 塞新字段。常见手机照片、长截图、源码和文档必须完成选择、准备、传输、移除、提交和源端读取；不能把内部缓存容量错误交给用户解决。支持大小根据实际各层限制确定并在选择前/传输前校验；不得以“无限大小不承诺”为由留下已知常见文件失败。

主要调整：`hapi/workspace-files.ts`、`shared/source-access.ts`、`workbench-types.ts`与来源工作区服务、`source-path-actions.tsx`、`source-file-actions.tsx`、`source-file-edit.ts`、artifact/document provider、`hapi/terminal-controller.ts`及源端 terminal owner 组合。原有拒绝向中央 Host 回退的保护保留。

验收：两台源机器有同名路径；分别完成查看、编辑保存及源端读回、产生一次外部修改冲突、下载和引用返回。启动终端后切 Pane、断开并重连，核对仍为原进程、输出不重复、输入不重放；显式关闭只影响该终端。常见大图和普通文件通过真实源服务，上传迟到、移除和刷新不串附件。写入只在隔离测试工作区执行。

### M5 · 让审批、问题、状态和技术详情各在合适位置

必交付 P0，不重做输入框和过程 renderer。

按已支持的原生请求类型，展示人能判断的命令、文件变更、范围、理由、选项及答案。原始 method、参数 JSON、内部错误进入默认收起的详情。请求卡保留原 session/request/turn 绑定，复用官方组件或公开 slots；不采用 HAPI 中“找不到旧请求就处理第一个”的做法，HHPI 当前精确目标策略继续保留。

多条待处理项以当前卡和紧凑列表组织，避免把大段参数与重复投递状态挤在输入区。只显示与用户当前决定相关的状态；内部 accepted/owner-admitted/observed 仍分别记录，默认文案表达“已保存”“已接收”“正在执行/等待你”，不把所有内部阶段逐条铺开。普通工具失败、重试和调试信息保留在原生过程详情，由 Agent 处理，不额外生成正文错误卡或重复摘要。任务确实受阻、需要审批或用户操作失败时，说明对任务的影响及下一步；呈现层级由用户影响决定。图片和计划仍位于主阅读路径。

对于动态工具调用等需要能力处理器的请求，显式登记支持范围；有可信处理器才执行，没有就保留原请求并给出可用去路，不自动批准、伪造结果或无声清掉阻塞。

普通 Agent 说明的质量同时按[交付方法第 5 节](hhpi-delivery-method.md)处理：核对受控源已支持的指令入口、作用范围和生效时机，要求说明提供新发现、影响和下一步，避免重复操作流水。保留客户端正文语义；真实源输出与混合内容 fixture 分别验证。外部源不可控时记录边界，不能用隐藏正文冒充完成。

主要调整：`remote-controls.tsx`、`remote-native-question.tsx`、`remote-elicitation.tsx`、状态文案与既有 tool/detail renderer。`liveProcessExpansion`、普通正文边界和用户手动展开优先级不变。

验收：审批、结构化问题、权限请求、多个并发请求与不支持请求；检查窄屏可读、动作可触达、旧卡不能处理新请求，原生结算后卡片更新。运行→正文→新过程→计划/图片→完成的内容层级保持。

### M6 · 交付独立后台通知、已读与更新恢复

必交付 P0。HHPI-only 必须有自己的后台通知路径；前台 toast 不作为本组完成条件，跨设备已读也不再仅作为未来占位。

**M6a · 通知服务。** 从 `source-notifications` 拆出浏览器订阅、设置界面、service worker、安装与更新 shell，迁到 HHPI 应用服务，删除原 HAPI provider 和 Hub API 调用。HHPI 应用 Host 提供同账号隔离的订阅保存、投递和撤销服务，复用 HAPI fork 已有的通知分类、Web Push 实现经验与依赖并保留许可证记录；复用代码解除 Hub 依赖，运行时不访问 HAPI 服务。服务端密钥不进入前端、仓库或日志。

Host 在浏览器关闭后仍观察已授权来源的现有事件，识别完成、失败和需要用户回答/审批，按源事件身份维护有界游标与投递状态。订阅属于账号/设备与来源授权，不属于 Pane；没有可见 Pane 时继续必要的轻量源观察，不保留聊天 DOM，也不轮询所有 transcript。首次基线和重连补齐不批量重报旧完成；确有缺口则补读相应事件范围，无法恢复时显示同步状态，不伪造通知。投递失败采用通知渠道自身重试，绝不重发 Agent 操作。

分别表达“应用已提交投递”“浏览器收到/展示”“用户实际读到”，不声称操作系统必然即时送达或恰好一次。可见页面提示和后台通知按现有 presence/实际阅读去重；通知摘要默认只含必要内容。权限拒绝、订阅过期、来源撤销、登出和服务端重启均有恢复或清理路径，旧账号订阅不能收到新账号内容。

**M6b · 回到原任务与已读。** 通知携带完整源身份和确切请求/内容位置；点击经认证进入原任务，已有 Pane 优先聚焦，登录后继续原跳转。旧请求已结束时说明结算状态，不把旧通知绑定到当前待处理请求。应用 Host 持久化按账号和源会话的阅读位置与手动未读意图，复用现有本地读者提交；旧快照和跨设备迟到更新不能撤销较新的有效意图。显示缓存、后台收到或打开列表均不自动标读。

**M6c · 安装与更新。** service worker、安装提示和更新检测独立于 `legacyHapi`；更新前完成草稿、附件、编辑文档及阅读位置 checkpoint，失败保留当前版本和工作。新客户端重新绑定原会话和操作，不能启动替身执行。通知与已读服务使用应用插件契约，不新增 HHPI Push/read-state wire；发布支持条件和必要配置进入无 HAPI 安装步骤。

主要调整：`client/index.ts`、`source-notifications/*`、`hapi/source-notifications.ts`的 provider 边界、`notifications/worker.ts`、`workspace/notifications.ts`、sidebar/read-sync 与更新 checkpoint；新增自有 Host 通知/已读持久服务及源事件订阅组合，不新增一套会话投影。

验收：未配置 HAPI、没有打开目标 Pane，手机应用退到后台后由隔离源产生待回答/完成事件；收到通知并进入确切任务，回答后其他设备状态收敛。再覆盖拒绝授权、重新订阅、源断开重连、旧通知、账号撤销和更新保草稿。仅调用推送 API 成功、SW 单测或前台 Notification 均不算后台体验通过。

### M7 · 以真实阅读结果完成现有可靠性与性能交付

优先级 P0。下面的重开窗口设计缺口已经由代码路径和隔离探针确认，纳入修复；其他性能优化仍由实际测量决定。

**M7a · 打开目标窗口与源状态追赶分离。** 默认重新打开进入最新窗口；只有用户明确选择继续旧位置、搜索结果或深链接时，才读取相应的 around 窗口。保存的阅读锚点用于“继续上次阅读”和未读定位，不强制把旧锚点至当前末尾全部读完。首次读取量 N 由最近视窗和有限预读决定，并受既有页面与字节预算约束；源端 seek 成本按现有索引记录，不承诺常数磁盘时间。

N 按目标呈现窗口估计，原生过程分组、消息修订和依赖需要的最小补读单独记录并受预算约束，不能把原始事件条数直接等同于可见行数。仍在打开状态的 Pane 保持当前阅读意图；本策略不把普通断线重连或增量误当成用户重新打开。

定点检查发现 `remote-history.ts` 从旧缓存恢复，再按保存版本订阅增量；历史 `hasAfter=false` 可被当成当前最新，`waitVersion` 与恢复也可能把窗口读取绑到全局追赶。隔离探针在缓存 841–1000、源端到 2000 且增量可重放时，观察到没有直接 latest 读取、回放 1000 条正文后 latest 返回 1160 条驻留内容。该结果说明特定路径缺陷，不外推为所有生产重开都走同一分支。现有 `remote-reading-session.ts`、源索引已支持 latest/around；HHPI 协议不变，不能把该策略缺陷归咎于必须修改 DSH Web。

H2 调整 `RemoteSourceHistory` 的打开/刷新策略：显式维护 latest、继续旧位置和定点目标，重新验证缓存的末尾事实；读取已有目标窗口并通过官方 reader/commit 呈现。源版本、操作对账和目录恢复各自推进，不以全量正文追赶为窗口就绪条件。快照与增量拼接继续按既有版本与代际契约处理，不能通过跳过断档检查换取速度。窗口外事件不得被无条件物化成正文；协议需要重放时仍正确消费，但不得阻塞目标窗口或扩大其内存/DOM。

| M7a 场景 | 必须观察的行为 | 失败判据 |
| --- | --- | --- |
| 缓存停在 1000，离开期间新增 1000 或 10000 条，默认重开 | 直接取得末尾 N 条，窗口正文、输入及导航可用；冷/暖缓存都成立 | 先读旧锚点到末尾全部正文，或等待全局追赶才可读 |
| 显式继续旧位置或命中远处搜索/通知目标 | 直接 around 读取目标附近；回最新走 latest；锚点失效有明确退路 | 逐页走完中间区间；把用户明确的旧位置意图覆盖成最新 |
| 两个 Pane 分别看旧位置与最新，同时有新事件/消息修订 | 两个窗口独立，源事实和操作状态正确收敛；保留可见读者 | 一方强迫另一方跟随；迟到结果污染新窗口；修订漏失 |
| 重放可用或已经过期，断线重连时仍有 pending 写入 | 分别走已有增量/快照恢复，窗口及时可读，写入继续按原回执对账 | 丢消息、盲重发，或借后台同步持续膨胀驻留正文 |

固定视口、N 与目标内容大小后，分别记录 Δ=0/1000/10000 的首屏时间、窗口 ready 前读取的正文条数/字节、请求数、驻留正文与 DOM，以及独立的后台重放量。目标窗口工作量应受 N 和页面预算约束，不随 Δ 线性增长；不能将后台流量藏进“零读取”，也不能用单次截图证明。该组合回归优先在现有读取/状态测试中执行，真实发布仍复用既有两条阅读场景。

**M7b · 连续阅读与资源。**

保留 RemoteSessionState 的快照增量日志、WorkScope、RemoteRecovery、共享观察和各 Pane 的官方 reader。新资源、新能力沿用原 owner 与代际，不能重新引入全局焦点/当前 session 的迟到写回。没有读者时释放聊天正文观察，不停止 Agent、队列或 PTY；M6 的 Host 通知订阅有独立的轻量租约，不能借通知保留整份 transcript 或隐藏 DOM。慢 Pane 不能拖住其他 Pane。

当前最近的 rc 记录仍未证明连续历史达到 80 ms 生产门槛。先在现有的两条有界阅读旅程中核对真实可见内容和帧间隔，区分读取、投影、publication、布局与图片解码，再定位修改。不预设“再加一层缓存”或“换掉 windowCommit”。不以旧日期的 83/117 ms 等测量冒充当前值，也不从测试 fixture 的行数预算推断整应用性能。

保留普通增量不触发恢复、预算内复用已读正文、保护所有可见读者、相同内容不重复 publication 的既有机制。当前全量 catalog wire 没有分页；本方案不承诺凭客户端优化得到端到端目录分页。

重开修复明确涉及 `remote-history.ts`、`remote-reading-session.ts` 与缓存/官方提交边界；其余测量候选仍是 `remote-reading*`、`remote-session-state.ts`、`remote-recovery.ts`、`surface/history-retention.ts`。源索引已有的定点能力优先复用；任何超出已批准 DSH 包级契约的扩展另列。

验收：桌面双 Pane 和窄屏长会话连续六段上翻，第二、第三次及后续均获得更早正文；往返锚点稳定，回到已读区间不重复取页，图片晚到不跳变，断线后不重发写操作。真实性能单独给实际结果。

### M8 · 主动发现 UI 错误，并维护完整工作流

主动检查作为 P0 交付要求，从第一组实现开始；产品文档整理仍为 P1。不另设漫长的“全面美化”阶段。

**2026-11-09 补齐二级面板交付要求：** 按[UI 交付要求](hhpi-proactive-ui-review.md#ui-delivery-contract)实施组件复用、默认信息层级、数字/时间格式化与实际看图。“队列与目标及同类二级面板的 UI 质量”属于原 M3/M8 功能任务；已有接口和操作证据继续复用，缺少实际画面与返回草稿证据时保持待验收。当前队列与目标面板的具体呈现和关闭条件以该规范为准，不按设备另拆任务。

把 README、feature-parity、source-view-architecture 与新 ADR 的关系标清：哪些是旧 V4/HAPI 路径，哪些是当前 HHPI 直连，哪些只是目标。README、QUICKSTART、HANDOFF 与 AGENTS 的目标统一为本机 DSH、官方 federation 与直连 Codex，删除 HAPI 来源安装和启用说明；旧材料明确标为历史迁移参考；修正“官方 DSH 版本已更新但旧基线和步骤仍像必需”的描述。没有必要为此改包名、配置目录或用户 ID。

执行[主动发现 UI 错误](hhpi-proactive-ui-review.md)中的流程：先把源码中的页面、菜单、弹层、命令、卡片和深链接整理为入口清单，再与六条用户旅程及来源能力对照。缺少入口本身就是待处理项；未出现的弹层、空页面和能力被错误隐藏的控件不能从清单中消失。

每次修改选取受影响的完整路径，包含入口、二级界面、操作结果和返回；共享样式、DSH 升级或 provider 变更时，还检查共同使用方。另按风险选择此前没有实际检查过的二级界面，避免每轮只看同一个聊天页。采用真实长度的标题、路径、草稿及混合内容；对该功能选择最容易暴露问题的失败、pending 或迟到结果，而非机械展开所有组合。

几何检查用于找越界、遮挡及错误命中；实际交互用于找无效按钮、错误对象和无法返回；Agent 必须看截图并判断信息层级、操作密度、状态文案和无意义留白。三种证据不能互相替代。保持当前原生组件与行为测试，真实键盘和物理设备单独记录，不恢复已删除的整应用夜跑 E2E。

发现问题后记录触发路径、实际/期望行为、具体图中位置、影响及对应模块。已授权范围内的明确缺陷直接修复，沿同一路径复验，并只在适合的层级留下必要回归。不能用“不是用户点名的问题”忽略同一工作流里的明显缺陷；超出任务的新产品方向另外列出。

这不是只写规范。每组实施都必须带完整入口和结果：例如做 fork 就同时做打开新会话、返回父会话、未决恢复和相关二级 UI，不能等用户分别提出四次。

复杂跨层及反复漏项的切片执行[独立查漏要求](hhpi-delivery-method.md)；审阅者的第一轮从原目标、原生基线和实际画面/操作出发，之后再看实现清单。UI 记录直接并入同一执行记录。主 Agent 还负责后续新任务的方法试行与回看，记录用户补报、重复确认、误报和成本；旧问题回放不作为新方法有效的证明。

**M8a · 手机键盘是必验收项。** 保留 `useWorkspaceViewport` 和紧凑原生输入框，不预判未测行为已经损坏。由 Agent 在可用的实际 Android 手机、实际浏览器和中文输入法上执行：中文组合与候选确认、换行和发送；长草稿加附件；打开 `/`、`@`、模型/权限菜单再返回；切 Pane、横竖屏、收起键盘及返回历史位置。发送/停止必须在可见区，候选和附件操作可达，组合输入不误发送，菜单关闭后光标与草稿保留。终端额外验证控制键、粘贴和软键盘 resize。iOS 支持声明需另有同类证据。

设备型号、系统、浏览器、输入法、构建版本和实际操作结果进入记录；先发现可用设备或既有远程设备控制能力，不直接要求用户代测。没有设备时明确记为尚未完成的验收任务，由 Agent 继续解决条件；不能因此删除键盘要求或把桌面窄屏改称真机通过。

**M8b · 全部已提供入口都有维护责任。** 第 6 节对 A1–P4 给出实现或保留核查的归属，特别覆盖分享/导出、设置取消、权限受限访问、更新恢复和移动端返回。已有入口发现断链则修，不因它位于二级页面或原来依赖 HAPI 而移出本次交付；只对第 4.3 节明确退役的 HAPI 专属产品入口移除。确实不适用的产品方向须写出具体边界，不用“按需”掩盖已承诺但未接通的能力。

| 第四阶段 | M0 关闭全部迁移与 R1–R10，删除残余配置/依赖/打包入口并完成无 HAPI 新装及升级验收；M3 剩余原生流程、A1–P4 未完成项及三条路径回归 | 每个适用能力都有入口、真实结果、异常恢复与返回；已有分享、设置等二级路径无已知断链 |
| 贯穿各阶段 | M8 主动 UI 审查；M7 实际性能与连续性；按已完成切片发布；基于真实 profile 直接改进执行流程 | Agent 主动进入二级状态、看图、操作并复验；新发现回写假设与任务；不发起 RSI 对照实验，也不能用速度掩盖遗漏 |

以上阶段均属于本次方案。P0 表示完成日常远程编程工作台必须具备，并非声称所有模块应同一天修改；纯文档整理等低风险收尾可穿插，但不能以阶段编号把必需能力变成未来版本。

### 并发责任与阶段依赖

上表描述交付依赖，不要求各阶段内的任务全部串行。初始上下文可按 M3/M5 原生任务、M4 文件与终端、M6 应用服务分配，后续以[开发任务 DAG](hhpi-development-dag.md)的实际依赖和文件归属领取，不固定三个代理各守一条流水线。来源、资源、账号契约分别完成即可放行后继；文件编辑不阻塞终端，通知不等待全部任务 UI。M0 的替代与删除归对应功能负责人，主代理关闭最终退出条件；M7 由主代理统筹，M8 随各功能实施。

精确写入文件、共享接口、局部验证和交接格式见[交付方法第 9 节](hhpi-delivery-method.md)。同一工作区不自动建立 worktree；共享写入串行，主代理统一构建和发布。名额释放后按触发条件安排独立只读查漏，复用运行证据。当前分工仍需在派发时核对实际文件依赖，不是把模块标题直接当作互不冲突的任务。

增量发布需形成可用切片的依赖闭包，并让共享 checkout 中的在途修改先收敛到明确完成边界；不能发布混有未完成修改的构建。真机和后台通知可以提前在命名版本上检查，后续受影响变化会使对应证据失效。最终发布节点只接受适用于最终版本的结果。

### 项目完成度如何判定

关闭每个切片前，核对需求依据与完整性审查、适用的独立查漏、逐行为实现/验证状态和未决工作是否有实际记录。缺失的记录补在同一执行文档；记录存在也不能替代下表的用户结果。方法效果的后续观察独立进行，不延迟已经验证的修复发布，也不提前宣称方法已降低遗漏。

用户已取消 RSI 对照实验，S2 从当前 DAG 与 V3 前置条件中移除。S1 保留实际用户路径判据。profile 用于定位真实工作中的浪费并改进脚本与调度，不再额外运行父/候选模型任务。

去除来源与完整工作台同时成立才算完成。下面八项与 R1–R10、A1–P4 共同作为关闭依据。

| 用户结果 | 交付关闭条件 | 不算完成的情况 |
| --- | --- | --- |
| 产品已完全退出 HAPI 来源 | 全新安装和旧安装升级都可运行；R1–R10 退出，旧工作可用，没有 HAPI 服务访问 | 只隐藏入口、关闭 flag、留下可选后端，或迁移丢内容/产生两个 writer |
| 能开始或继续正确任务 | 仅通过保留的 DSH/Codex 路径完成发现/创建/恢复/设置/首条提交；分支打开确切目标 | carrier 存在；列表出现类似标题；必须回 HAPI 才能继续 |
| 能参与运行中的任务 | 输入、附件、命令引用、队列、计划、问题审批、Goal/子任务等适用动作有真实结算与恢复 | 按钮存在；只写“已接受”；请求/结果落进通用 JSON 面板 |
| 能处理编程成果 | 图片/媒体/文档/Diff 能读，源文件可编辑保存并处理冲突，引用/下载后回原工作 | 只有只读预览；源端没有收到修改；保存失败导致草稿消失 |
| 能可靠使用源机器终端 | 真实 PTY、控制权、手机输入、断线同进程恢复、显式关闭均验证 | command/exec 输出；重连创建新 shell；接到中央 Host |
| 能离开再回来 | 后台真实收到通知、认证后到原请求，跨设备已读和更新 checkpoint 有证据 | 只有前台 toast；API 返回成功；浏览器关掉后无人观察来源 |
| 手机和多 Pane 可实际使用 | 真机键盘/IME、辅助页面返回、草稿/光标/阅读位置保持；桌面与窄 Pane 关键动作可达 | 只测 390 px；没打开菜单；输入框可见就算通过 |
| 能稳定阅读与维护安装 | 大跨度重开直接取得目标窗口、显式旧位置可恢复；既有连续历史和 80 ms 门槛实测通过；版本、权限、撤销及迁移通过 | 先追完中间全部事件才显示当前窗口；构建/单测替代生产体验；未测却报完成 |

最终交付记录逐行给“通过、失败、未执行、不适用及依据”，并附版本/环境/来源。必交付项存在失败或未执行时不宣称整体完成。源端确实不存在的 Agent 功能可记不适用，但必须有固定版本证据；已由 DSH 或自有服务承载的文件、终端、通知不能借此排除。允许明确记录不阻断工作的小问题，不保证没有任何未知 bug；已发现的主要流程断链、误操作、数据丢失、显著遮挡或诊断刷屏必须处理。

### 明确的边界不等于遗漏

不承诺无限附件大小、终端跨源 owner/Host 重启仍存活、第三方操作系统通知必然即时送达、源端无法提供的原生动作，或没有确切关联证据时自动猜出创建结果。相应的合理限制、错误与恢复路径仍需实现。文件保存、PTY 和后台 Push 已有上述实现责任，不能继续归入这张限制清单。

不新增无具体失效依据的 hash 校验、大锁、普遍审批或多层缓存。现有认证、原生裁决和发布保护保留。实现时先核对已获准的 DSH 包级范围，范围内不重复请示；只有确实超出已有授权且无法用公开接口完成，才列明包、契约和必要性另行处理。本轮没有提出新的扩展批准请求。

## 8. 按现有测试体系验收，而不是再建一套重流程

以下是后续实施时的验收方案，本轮没有执行产品测试或真实 Agent 写操作。

| 旅程 | 必须覆盖的断点 | 合适的证据 |
| --- | --- | --- |
| 继续旧任务 | 原 HAPI 来源精确转移、旧链接及草稿恢复，原生身份和唯一 writer；目录缺项、断线、不同 Pane 阅读位置、已有草稿 | 核心契约 + 既有真实历史旅程 |
| 带上下文开始任务 | 新建来源、选图上传、引用、设置、首次发送、回执不明 | 原生组件 + 合成源写入；真实源接入单独记录 |
| 运行中参与 | 审批/问题、队列、插话、停止、父子任务 | 确切源目标、原生回执与最终状态；仅合成会话写入 |
| 使用工作结果 | 图片、文件、计划、Diff、编辑保存、外部修改冲突、管理、引用及返回 | 生产组件、真实源端读回、授权拒绝、窄屏布局和导航 |
| 多任务与二级界面 | 切 Pane/窗口、设置、源终端、隐藏/关闭视图、真机键盘 | 原进程与源目录、断线屏幕和输入确认；草稿/焦点/阅读位置；实际手机操作 |
| 离开后回来 | 新增大量事件后的最新窗口、显式旧位置、通知定点；后台通知、已读同步、刷新、更新与撤销 | 目标窗口读取量与独立同步量、两个 Pane 的位置；真实设备投递与返回、原操作恢复、checkpoint；生产探针仍只读 |

开发按 [testing.md](testing.md#L1)使用选测、契约与 DOM 行为测试；现有发布仍保留完整检查、故障检出和最多两条有界浏览器场景。真实键盘、IME、滚动及源端执行分别给证据。已有测试文件存在、构建成功、截图生成和 HTTP 200 都不构成整条工作流通过。

执行去重和停止条件见[交付方法第 8 节](hhpi-delivery-method.md)：子代理不各跑一遍全量套件或部署；主代理选择包含必要检查的统一发布入口，验证后合入的修改重新按影响检查。同一版本、同一环境且未受后续修改影响的证据可复用，不新建测试平台，也不改变既有发布脚本的保护。

### 删除范围的验证安排

源码和产物审查覆盖 R1–R10 的实际引用、动态注册、导出与安装清单；离线迁移用真实格式的隔离快照验证，覆盖重复运行、中途失败、身份歧义、附件缺失和未决请求。独立启动/升级在现有安装与进程内契约层验证，不另开整应用 E2E。旧后端被删除后的测试应删除或改写；草稿、授权、断档、断线和多 Pane 等通用保护迁到原生路径，不随旧代码消失。

当前 [testing.md](testing.md) 仍有旧 HAPI 标题选择和 SourceFrame 测试说明；实施时更新失效的来源与 fixture 路由，保留同等用户行为断言、连续阅读要求及现有发布预算。本轮不修改测试脚本或规则。生产 HAPI 服务无需停止，使用隔离环境、运行时服务表及网络证据验证独立性。

### 主动发现与回归验证分别承担什么

现有用例已经会打开工具输出、Diff 和图片，并检查宽度及编辑器命中，见[官方组件实验室](../tests/browser/README.md)和[实际呈现用例](../tests/browser/codex-rendering-journey.mjs)。应复用这些能力。它们不覆盖完整工作区的所有菜单与页面，也不证明默认信息层级合理。例如，编辑器可见且页面没有横向溢出，仍可能出现输入区过高、权限状态占一整行、主要操作埋在多级菜单中的问题。

[截图采集器](../scripts/test-smoke-capture.mjs)明确保留 `visualReview: required`、`interactionChecks: not-run`。后续必须由执行 Agent 实际看图、操作并补写结论，不能因采集退出码为零就把两个状态改为通过。代码审阅发现疑点、截图确认视觉问题、交互复现故障以及源端执行结果，分别标注。

详细的入口清单、场景选取、几何检查边界、看图问题与问题处理见[主动 UI 检查方案](hhpi-proactive-ui-review.md)；跨层独立审阅、统一执行记录及方法效果评估见[交付方法](hhpi-delivery-method.md)。这些是待执行安排，本次没有运行产品 GUI 检查。

### 发布预算不等于全产品覆盖

`test:smoke:history`的桌面/手机检查已经占用现有两条、每条 60 秒的发布 UI 预算。受影响 UI 检查需要在同一场景内编排，不能再运行两条就说“仍是两条”。实验室场景的合成源、外壳和 IO 边界也不能被转述为已部署的完整工作区。

若关键受影响路径无法在现有预算内验证，就缩小实施切片，并把尚未验证项保留在整体交付清单中；不能把清单删小后声称项目完成。不得删除历史断言、延长超时、拆成多轮规避上限。独立完成且已验证的修复仍按既有规则发布。入口清单可一次盘全，运行证据只覆盖实际执行的页面与状态。

### 真机与后台通知的有界验收安排

这两项需要补充设备证据，现有桌面/手机视口两条场景不包含它们。本方案明确提出一次平台验收安排：键盘与菜单输入一段、退后台收通知并返回一段，各以 60 秒为执行上限，环境准备和设备版本预先记录；终端手机输入并入对应受影响场景，超出则明确记录未完成，不通过延时蒙混。只使用隔离测试会话和工作区，原生源执行与实物设备分别记录。

这是拟增加的设备验收任务，不冒称“仍然只有现有两条发布场景”，也不暗中改写 `AGENTS.md` 或 `testing.md`。实施前按现有测试规则明确新增任务与预算的适用范围；现有发布浏览器上限仍保持。若现有规则确实不允许所需设备验证，则提出这项具体规则调整，而不是删除真机和后台通知交付要求。设备不具备或检查失败时整体状态保持未完成，由 Agent 推进条件与修复，不转交用户兜底。

### 性能与资源预算随能力落地验证

文件树按展开目录读取，预览沿用有界读取与官方资源缓存；文件观察按打开资源共享，关闭后释放。PTY 沿用 DSH 输出窗口、保留与空闲回收规则，不无限缓存输出。通知在 Host 消费轻量事件和有界游标，不为每台设备重复读取整段历史；大图片在本机准备，二进制内容不重新塞进 localStorage 操作日志。M7 对打开、输入、滚动、Pane 切换及相关源请求量给实际前后结果，不预先编造提速百分比，也不允许后台新服务破坏现有阅读门槛。

## 9. 本轮交付边界

这份文档以彻底删除 HAPI 兼容来源为最终架构，保留完整工作台交付责任。M0 负责退役、迁移及独立运行验收，M1–M8 负责替代服务和完整用户流程；A1–P4 的原生接入、数据、能力和体验要求不因删除旧后端而缩减。文件保存、可靠终端、独立后台通知与真实手机键盘验收均纳入本次任务，不再以含糊的“原生契约待具备”留到未来。

第四至七次修订分别补充了退役迁移、调研方法、快速验证与并发 DAG。第八次修订基于最新失败研究及重开路径审查，更新需求假设、M7a 目标窗口、组合验收、独立审查和 S1/S2；已知要求、节点、证据层与新发现的关系同步到配套文档。此前关于组件实验室、呈现用例和测试规范的证据仍按原范围使用。当前线上性能与物理设备行为需在实施中核实。本轮只改开发计划及其数据/图，不改 HHPI 协议、产品代码、AGENTS、测试规则或运行中的 harness 策略；没有执行产品构建、部署、模型实验或生产写操作。文档检查和本轮 profile 记录不算产品验收，方法效果仍待真实任务评价。
