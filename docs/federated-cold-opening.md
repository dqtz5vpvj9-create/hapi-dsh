# 远端会话打开性能：2026-10-24

本轮修复的是保存布局中的远端普通 DSH 会话。此前的本地 HAPI 源会话验收没有覆盖这条路径，不能用它证明远端冷开性能。

## 改动与原因

- 远端图之前绕过分阶段加载，首次打开会下载包含 Account 的完整组合包。现在阅读先加载必要图，通过该远端 Host 的设置入口再加载完整官方插件图。
- 远端插件 URL 带版本，响应也是 immutable，但客户端强制 `no-cache`；服务器没有 ETag，因此刷新仍重新传输整包。移除此覆盖后，第二次导航的远端插件传输为 0。每个 Host 的版本、认证和模块实例仍各自独立。
- 自有初始化调用 `sessions.refresh()`，与官方连接建立后的目录刷新竞争，导致一次导航扫描两遍整个远端目录。现在由官方连接代际负责首次刷新，自有代码只观察公开列表状态。
- 本地 Session provider 已使用 20 条首屏窗口，远端 follow 却仍使用默认 500 条。现在通过公开连接载体为首次 follow 应用相同窗口，官方分页仍决定连续边界和游标。重连保留官方原请求，避免把已翻出的历史缩回 20 条。

没有修改上游源码、会话执行权或历史存储。仅构建并发布客户端，发布前后 Host PID 相同。客户端资源版本为 `f5054040fbb8`。

随后继续验证时发现 Host 自动 OOM 重启；这发生在前端发布完成之后，前述 PID 相同只指发布前后的即时检查。日志显示曾接近 4GB 堆上限，另已复现流式切片保留全部历史前缀的内存缺陷。其基线、机制和修复验证见 [内存分析](memory-breakdown.md)，不能把前端传输提速当作后端 OOM 已解决。

## 生产时序

同一既有远端会话，常驻生产 Host，桌面 Chromium 1440×900；每组使用新的浏览器 context，随后在同一 context 刷新。计时从文档导航开始，到真实可见正文或可编辑输入框。HTTP 模拟 120ms 延迟、10Mbps 下载；WebSocket 经过只读过滤，不保证受相同限速。

同一严格过滤策略下的逐次样本如下。它们不是 p95，也不是用户线路测量。

| 版本 | 冷开正文 | 冷开编辑器 | 缓存刷新正文 | 缓存刷新编辑器 |
| --- | ---: | ---: | ---: | ---: |
| 修改前 | 12.899s | 10.835s | 10.141s | 8.374s |
| 远端分阶段加载及 HTTP 缓存 | 11.818s | 9.936s | 4.923s | 3.044s |
| 再移除重复目录刷新 | 8.943s | 7.055s | 4.402s | 2.464s |
| 再应用首屏历史窗口 | 9.376s | 8.348s | 4.170s | 3.274s |

冷开总 HTTP 传输由 7,814,861 降至 5,244,051 字节；缓存刷新由 5,080,105 降至 217,838 字节。远端插件本身由每次导航 4,668,992 字节变为冷开 2,245,197 字节、缓存刷新 0 字节。新窗口将该组编辑器到正文的间隔从约 1.9 秒降至约 0.9–1.0 秒，但整次冷开受到其他阶段波动影响，没有按相同幅度缩短。

旧过滤策略阻止了 `session/control`。检查 rc.3 实现后，确认它仅输出投影基线和更新，已将它加入最终探针的只读许可表。保留该正常状态流后的另一组样本：

| 导航 | 正文 | 编辑器 | 最长主线程任务 |
| --- | ---: | ---: | ---: |
| 冷浏览器 | 8.537s | 7.574s | 330ms |
| 第一次缓存刷新 | 3.824s | 2.917s | 146ms |
| 第二次缓存刷新 | 5.711s | 3.107s | 175ms |

此外，未施加 HTTP 限速的旧严格探针测得冷开 4.009 秒、缓存刷新 7.200 秒。后一轮远端目录 RPC 独自耗时 3.032 秒。该慢样本保留，不能只引用较快结果。

## 尚未达标的开销

正常状态流冷开样本中，主工作区出现于 3.797 秒，远端必要插件图就绪于 6.448 秒，编辑器于 7.574 秒出现，正文于 8.537 秒出现。剩余关键路径仍包含主图和远端图串行初始化、远端目录、首屏历史和渲染；缓存不能消除这些步骤。330ms 长任务仍然存在，远端目录和历史读取也有明显波动。

因此本轮证明减少了重复传输和重复工作，**没有证明达到原 HAPI 的打开速度，也没有证明远端冷开、主线程长任务或尾延迟已经完全解决**。没有测物理手机或用户实际网络。后续需要分别缩短两层初始化的串行等待、远端目录读取和历史就绪时间，不能再用热切换成绩替代它们。

## 验收与复现

- 类型检查通过；全量逻辑测试 1172 通过、1 跳过。
- `e2e/federated-cold-boot.spec.ts` 的两个用例分别通过：真实官方 Hub/Runner 的冷恢复、缓存刷新、单次目录请求、远端设置按需加载；20 条首屏、连续向前滚动、重连后的历史和草稿、实时消息。
- 向前滚动用例最初只发一个巨大 wheel 事件，在官方视图尚未退出跟随末尾时未触发分页。改为持续可信滚轮输入，跨过该状态转换后验证最早消息确实出现；未修改产品滚动策略来迁就测试。
- 固定 webshot 命令采集并实际查看合成和生产的 1440×900、390×844 截图。正文、标题、输入框和底栏可见，无横向页面溢出。生产只读代理阻止保存布局，截图中的 403 布局保存提示由此产生，不能当作产品正常运行的截图状态。
- 所有生产读取阻止发送、新建会话、保存布局和执行操作。当前探针保留 `session/control`，仍是受过滤的浏览器访问，不冒充未经干预的测量。

复现命令及探针边界见 [UI 验收](ui-acceptance.md)。原始逐次样本保存于本机 `/mnt/cache/data-cache/hapi-dsh-federated-{before,after,final,window-final,normal-streams,unshaped}/report.json`，测试日志和截图保存于同一临时目录；这些含运行环境信息的材料未提交到仓库。
