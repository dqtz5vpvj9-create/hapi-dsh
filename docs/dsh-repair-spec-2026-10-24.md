# HAPI 架构对齐与完整会话验收 spec

本版替代本文件此前的“尾页先显示、全归档完成后换代”目标。用户要求点击后直接得到 HAPI 那样完整、可操作的会话，不接受“先显示但不能翻历史 → 会话不可用 → 最后完整”的打开路径。本文是实施与验收要求，不是修复完成报告。

## 1. 唯一产品目标

一次打开，一个持续可用的会话。目标会话第一次呈现时，正文、输入框、历史滚动、阅读导航及实时订阅必须属于同一个有效的源会话，随后保持可用。正常补页、目录刷新、显示租约恢复、后台归档都不能让用户经历另一个会话、禁用画面或重新初始化。

“完整”指交互能力完整，不是把全部历史加载进浏览器。长历史必须按需读取；正文窗口之外的数据可以未驻留，但其分页游标、读取路径和导航能力必须已经可用。不能通过把所有历史预加载完再显示来满足本要求，也不能先展示一个不能操作的半成品来降低打开耗时。

打开只有一个验收成功条件 `conversationUsable`，不是三次成功或三个产品状态，也不是要求增加新的 Host 全量 ready 状态机。网络请求、渲染等内部步骤可以记录为诊断 span，但不能作为用户完成指标。真实断网、权限拒绝、源删除仍需准确表达；后台正常初始化不能伪装成这些故障。

## 4. 以 HAPI 当前实现为架构基准

必须阅读实现，而非只引用 `docs/chat-experience-contract.md` 的旧目标。源码引用与差异核对见 [HAPI 架构调查](hapi-architecture-target-2026-10-24.md)。父线程已核对以下边界：

1. **源身份与操作连续存在。** HAPI `web/src/components/SessionChat.tsx` 把 `HappyComposer` 按源 session ID 绑定，输入区与 `NativeCodexThread` 正文分开。正文窗口同步和分页不能决定编辑器实例是否存在。HAPI-DSH 也必须把源身份、操作控制器、草稿及未决回执保存在稳定 owner 中，不依赖一次全量投影的生命周期。
2. **按需历史是正常数据路径。** HAPI `web/src/hooks/queries/useMessages.ts` 订阅已有 message window，并单独请求 tail/older；`web/src/lib/message-window-store.ts` 维护窗口、游标、epoch、历史缓存和读取取消。窗口扩大或换页不会创建另一个业务会话。HAPI-DSH 必须采用等价的有界窗口与游标路径，不能把缺失旧前缀当作历史重写。
3. **渲染随人类阅读范围工作。** HAPI `NativeCodexThread.tsx` 的 `NativeSeat` 按 ID 订阅节点，`NativePageCommit` 在 DOM 改变前保留阅读位置，`WindowedMessageList` 控制挂载范围。投影、DOM、解析与大输出展开按当前视口和有限预取分配，不随所有曾访问会话或整个归档增长。
4. **只有一个滚动位置所有者。** HAPI 的 viewport/scroll/navigation 协作持有阅读意图。HAPI-DSH 不增加第二套互相竞争的滚动修正器。补页以稳定源节点和视口偏移接续，不能停在新页顶部，再跳回旧位置。
5. **实时流合入原窗口。** 增量更新、重连补齐、终态、队列和审批沿原生身份去重并有序合入。目录刷新不是清空正文或重建整个会话的理由。全量归档扫描不得占住这些交互通路。

目标数据流是：原生 HAPI 源身份与控制 → 有界的消息窗口/游标和增量订阅 → 官方 DSH 内容映射及 Conversation → 当前视口。草稿、原生投递与审批由稳定源控制器管理。导航目录可以保存轻量索引，点击目标再读取相应窗口；不能要求载入所有正文才能显示 minimap。

继续复用 pinned DSH `0.2.1-rc.3` 的公开 provider/slot/controller 接口。不修改上游或 node_modules，不另做通用聊天渲染器。先证明这些公开接口如何承载稳定源身份、可向前分页的窗口和阅读导航；若存在不可跨越的 API 限制，写清具体接口、源码与最小失败用例，标记阻塞。不得悄悄退回尾页临时会话、全归档重建或延迟禁用画面，并仍声称符合架构。

真正的源 rewind、fork、epoch 变更必须保持原有身份与权限隔离，拒绝旧请求覆盖新数据。对这类少见变更的处理不得成为每次普通打开都换代的借口，也不得让旧编辑器指向另一个原生线程。

## 5. `conversationUsable` 的行为判据

所有条件同时成立，才记录唯一打开时刻。仅有布尔 ready、DOM 节点或 `reference.ready` 均不足以证明。

| 能力 | 必须检查的实际行为 |
| --- | --- |
| 正确目标和正文 | 私有清单中的精确源身份；标题不回退；源端独立确认的当前数据/阅读位置真实出现，无旧会话混入 |
| 输入 | 唯一可操作的官方编辑器；真实焦点和文本输入成功，未发送草稿保留；没有 inert、遮挡、“会话不可用”或假启用；来源控制器路由到正确源 |
| 向上翻历史 | 从第一次呈现开始就用可信 wheel/touch 操作；能滚动已有窗口，到边界立即走有效分页；不得等待全归档或先点击补页预热才能操作 |
| 阅读导航 | 当前布局应有的 minimap/目录从首次呈现就可见并可定位；点击已有较早目标可以按需取窗口，不能只有空壳或依赖全量正文索引完成 |
| 实时 | 当前源订阅有效；正常增量在当前实例中出现，读旧消息时不抢位置；不能等回复结束才一次刷新 |
| 稳定性 | 补页、后台工作、目录更新和重连不替换正常会话的源控制器、编辑器和滚动根；不短暂禁用，不清空，不重新显示 loading |

第一次实际呈现给用户的目标画面已经含正文却缺少任一上述能力，记为 `partialConversationExposed`，该次打开失败。即使后来 `conversationUsable=true` 也不得翻转为通过。浏览器一个绘制帧以内、尚未呈现给用户的 React 内部装配顺序不另算产品状态，但出现过的不可操作帧必须保留。打开过程中可以维持仍然可用的原页面，但必须仍计入点击到目标完整呈现的耗时；不能用长遮罩、旧页面滞留或长 loading 来隐藏超时。

补页的网络等待只影响尚未取得的数据，不应冻结已取得正文、草稿或操作。真实断网保留可读内容及可编辑草稿，并准确说明发送能力；不能强行把离线发送标成成功。源端拒绝与本地生命周期断裂必须在证据中区分。

## 6. 测量口径与门槛

窄屏遵循官方响应式布局：容器 ≤900px 时桌面 TurnNavigator rail 可隐藏，这不等于历史或阅读导航失效。宽屏目标必须从首次呈现就能使用该 minimap；手机检查适用入口及历史操作，不能用隐藏的桌面元素冒充可用。

只有 `click/navigation → conversationUsable` 可作为打开成功耗时。正文首次像素、编辑器节点出现、Host ready、socket open 仅用于分解瓶颈，不得用其中最早值做 KPI。任何 `partialConversationExposed` 或后续可用性退化直接失败，不受平均值、最终时间或截图结果抵消。

- 已缓存会话：完整可用 p95 目标 <150ms，每次 <500ms，沿用原先的即时打开预算，但把对象从正文改成完整能力。
- 本地首次源挂载：完整可用每次 <1500ms，沿用原工程上限；不是对用户网络“已经达标”的声明。
- 在同一机器、浏览器、网络、目标源、历史位置和运行负载下测当前 HAPI 与 HAPI-DSH。完整打开、滚动、重连的全部样本分别报告。配对打开 p95 允许的工程测量差额最多为 `max(50ms, HAPI p95 × 10%)`，同时仍须满足已有绝对上限；这是本 spec 新设的比较容差，不是声称用户以前给过该数字，不能因失败而放宽。未取得同条件 HAPI 数据，不得声称已达到 HAPI。
- 旧文档的冷浏览器 <6000ms 是旧流程记录，不能作为本次“跟 HAPI 一样即时完整”的达标依据。文档启动、会话打开分别计时；冷网络绝对预算需要先取得同条件 HAPI 基线。不得因为网络更慢就改计时起点或隐藏请求时间。
- 静止补页同一锚点逐帧漂移 ≤1 CSS px；顶端持续手势分页提交时同一旧锚点补偿误差 ≤2px。连续滚动帧间隔 p95 ≤50ms、最大 ≤200ms，并与 HAPI 同条件对照；不能称为 60FPS 保证。
- 合成源六次独立增量各自 <1500ms 且在结束前可见。真实会话用自然产生的源事件测到达与绘制时间；测不到时标未测，不为了通过而发生产消息。

缓存打开至少 20 次；首次源挂载和新浏览器各至少 5 次，HAPI 和 HAPI-DSH 交替串行运行，保留所有样本及失败。小样本分位数只作为描述，不夸大统计置信。浏览器冷、Host 冷、源 attach 冷、缓存热分别注明，不把已有完整投影的热打开叫冷打开。

3. 连续执行翻旧历史、反向滚动、展开长工具输出、minimap 定位、回到最新、刷新恢复、网络中断恢复。观察到后台归档任务结束或被架构移除，并继续至少 30 秒；60 秒诊断截止没有结束则判失败，不能将截止时间当性能预算。
4. 先从源端取得一个确定的消息游标/水位与标题，验证视图至少覆盖该水位并继续接收后续增量，不能追逐不断变化的“最后文本”使计时无起止。正文片段只作辅助证据，公开日志不记录它。
5. 原版反例必须包括：正文可见但不能滚动；编辑器先可用再禁用且最终恢复；minimap 延迟才有功能；完整归档触发 Session/编辑器换代；已知标题回退；首次成功后第 6 秒与第 20 秒失效；透明/旧/inert 画面冒充目标。每条都必须让新观察器报错。

## 8. 实施顺序与内存责任

先做一条纵向切片：**当前真实源身份 → 稳定操作控制器 → 有界初始窗口和可用历史游标 → 官方完整会话 → 普通补页不换代**。先用该路径的负对照和行为断言约束实现，再扩展到 observed 引擎、远端 Host、多 Pane、关闭/重开和后台恢复。禁止继续单独优化“最早正文出现”。

必须移除普通历史补齐导致的显示 Session 重建，不能只修 `unavailable` 字符串或增加重试。历史数据、实时订阅、草稿和原生操作的生命周期应明确分离：关闭 pane 可以回收显示窗口和缓存引用，不能 abort 原生执行；重新打开可以重新读取窗口，不能丢未决投递或让旧 owner 操作新源。

为原始页、投影窗口、展开大输出、后台预取、warm cache、在途事件分别给出字节预算与所有者。总预算包含活动与非活动对象，不能只限制 Map 条数。保留完整单项大输出的按需读取能力，不截断、不加堆上限、不定时重启。主线程只处理可见窗口提交和必要交互；解析/投影可分片或 worker 化，但必须记录总 CPU、峰值/留存内存和取消成本，不能用搬线程掩盖全量复制。

既有 128 项 / 8MiB 事件队列、UTF-8 缓存预算、取消传播与租约回收修复保留；仍需检查整体持有链。压测至少跨过历史约 14.4 分钟 OOM 窗口，在固定规模多源打开/关闭中保留一个持续活动源，验证逐事件内容无漏无重。自然 heap、GC 后 heap、external、RSS、浏览器 DOM 分列；遗漏同步峰值的采样不能称总峰值。内存未进入预算平台就保持 FAIL。

## 10. 交付、独立验收与立即发布

DSH subagent 负责有边界的实现与原始证据；父线程阻塞等待并独立读 diff、核对断言、查看截图，重跑最可能假通过的用例，手动修正漏测和不实结论。产品修复仍须相应 typecheck、逻辑回归、构建和官方 Host 行为测试；文档修改只检查内容、引用与 diff，不为凑数运行全套测试。

报告必须逐项写 PASS / FAIL / UNVERIFIED / INVALID-TEST，以及目标别名、运行环境、源版本/构建标识、完整可用时间、退化事件、请求阶段、CPU/内存、失败与重试、截图是否实际查看。没有实际执行的新增断言写未执行，不能算已建立测试基建。没有本次真实会话通过，最终结论不得写“可用性已修好”“与 HAPI 等价”。

用户已授权每次完成的修改立即发布。父线程对已验证的增量按现有正式流程立即上线，核对线上构建和实际目标；未解决项同时报告，不因全项目尚未清零就把已验证改动留在本地。仅前端改动不重启 Host；需要更新显示 Host 时保留普通 DSH 执行检查及回退构建；不得重启 HAPI Hub/Runner 或结束当前原生任务。文档通过 Git 推送发布，不为文档重启服务。

不扩大写权限、不新建 worktree、不修改 HAPI 或上游。临时证据在 `/mnt/cache/data-cache`，无凭据/正文/私有身份入 Git。历史失败与负对照保留；重试不得覆盖失败。已提交、已上线、已验证和未解决必须分别陈述。
