# HHPI：把调研方法落实到每次交付

状态：当前交付执行规范；原 2026-11-07 规划内容保留，配套[主计划](hhpi-product-change-plan-2026-11-07.md)。产品实施已恢复，实际实现、发布与缺口以[当前交付记录](../artifacts/development/hhpi-delivery-20261107/current-integration-20261108.md)为准；本规范本身不代表要求已经执行到位。

当前执行以用户最新决定为准：RSI 对照实验取消；主代理按完成或阻塞事件介入，子代理负责完整路径及集成；确定性检查、依赖与构建交给可复用的脚本流程。手机验收与帧率调优已停止，不按设备复制功能任务。具体执行方式见 [profile 执行规则](development-profile-rsi.md)。

本规范适用于 M0–M8 的实施与验收。它补齐需求依据、独立查漏、长任务交接、Agent 输出和方法效果评估的执行责任。产品范围仍以主计划为准：删除 HAPI 兼容来源，保留 HHPI v1，交付原生 DSH/Codex 完整工作台。

执行记录已有可运行的[profile 与 harness 改进工具](development-profile-rsi.md)：保存 DAG 任务、耗时、行为证据和用户补报，生成时间线，保留历史策略记录。RSI 对照执行已取消；实际工作中的改进按 [开发经验](development-practices.md) 复用，组件结果与完整用户路径分开记录。

主计划回答做什么；本规范回答怎样避免遗漏、怎样留下可核对的结果；[主动 UI 检查](hhpi-proactive-ui-review.md)负责具体页面和状态的检查方法。三者共用实施记录，不各维护一套完成清单。依据来自[此前的文献调研](/mnt/cache/src/.lavish/agent-completeness-20261106.html#recommendations)；下文的触发条件、职责和记录格式是本项目的工程选择，不是论文已证明有效的固定流程。

## 1. 开工、交付和续接时怎么执行

执行主计划时先读本节；跨层接入、共享能力变更或反复漏项时读第 3 节；长任务换上下文读第 4 节；涉及过程与普通说明时读第 5 节；首次试行和交付后回看读第 6 节。开发选测和发布去重按第 8 节，Codex 并发实施按第 9 节，新增文献及适用边界见第 10 节。小改动复用相关行为和证据，不强制展开整份模板。

| 时点 | 承担者与动作 | 必须留下什么 | 何时完成 |
| --- | --- | --- | --- |
| 开始实施主计划 | 主 Agent 核对最新用户目标、全部 A1–P4、R1–R10、三条原生路径及既有批准；审查要求本身 | 同一实施记录中的目标、决定、需求依据、遗漏/矛盾和处理结果 | 必要行为有归属和可观察结果；未解决依赖保留，不能因难做而删项 |
| 开始一个功能切片 | 实现者列出从正常入口到源端结果、恢复和返回的完整行为；选择所需证据层 | 行为行、涉及的相邻入口、版本/环境、验证安排 | 能判断用户何时做成；没有把“RPC 可调”写成产品完成 |
| 实施过程中 | 实现者完成路径，按 UI 方案实际操作、看图、核对源端；发现同目标内的明确缺陷直接处理 | 实际结果、发现来源、修复与同路径复验；新需求依据及必要决定 | 已验证部分可独立交付；未完成行为仍在总范围内 |
| 宣布切片完成之前 | 按第 3 节由同一 Agent 切换视角，或由独立上下文审阅者从原目标查漏 | 首轮独立发现、与实现清单的差集、复核结论 | 必要缺口已处理或明确保留为未完成；不能自行缩小目标后报完成 |
| 交付与上下文切换 | 主 Agent 对齐行为、证据、遗留项和下一步；接手者先恢复记录再继续 | 第 4 节的同一执行记录及简短用户交付说明 | 每个完成声明可追到实际版本和证据；既有授权无需重新索取 |
| 后续同类任务交付后 | 主 Agent 更新第 6 节的观察数据，解释收益和代价 | 用户补报、回归、重复确认、审阅耗时和误报 | 有实际观察才讨论效果；数据不足保持未评估 |

## 2. 先审需求本身：依据、遗漏、矛盾和错误假设

### 2.1 每个行为说明为什么属于任务

行为用“用户在什么状态下，通过哪个入口，对哪个对象做什么，看到什么结果，怎样继续”描述。一个 API 名称、一个文件名或“支持附件”都不足以作为完成标准。

依据分三类，可以并列：**用户明确要求**，链接具体决定或本计划条款；**原生基线**，给出固定版本、入口和实际能力；**目标必需**，写出缺少它会阻断哪一步。HAPI 的参考实现不是自动扩张范围的授权；源方法表里缺少文件保存，也不等于源机器工作区不能提供保存。

下表把这轮容易漏掉的行为落实到现有计划。它是待执行要求，不是当前缺陷清单或通过记录；实施时将其行为行纳入同一执行记录，并按切片补全所有适用的 A1–P4 和 R1–R10。

| 行为与归属 | 需求依据 | 需要核对的假设 | 完成所需结果 |
| --- | --- | --- | --- |
| 无 HAPI 新装、旧安装转移后继续原任务；M0 / R1–R10 | 用户明确要求删除兼容来源；继续原工作是该目标必需 | 删除 Hub 接入不等于删除用户数据或另起执行者 | 原身份与唯一 writer；旧草稿/附件可用；产物和网络无旧后端 |
| 分支后到确切新会话，再回父任务；M2/M3 / K3 | 完成分支这个用户目标必需 | RPC 返回、目录出现相似标题是否被误当作完成 | 正确新目标、父草稿保留、丢回执不重复创建 |
| 附图、命令、引用从输入到源端结果；M2/M3/M4 / C3、D1–D4 | 用户明确要求；保留原生编辑器基线 | 上传触发时机与上传内部本机准备是否混淆；候选插文本是否冒充结构化接入 | 正常入口可操作，源端收到正确内容，刷新/移除/迟到结果不串对象 |
| 编辑源文件、保存、冲突后继续；M4 / I3 | 用户明确要求；完整编程工作台必需 | DSH workspace-files 的只读能力是否被当成保存能力 | 正确机器写入并读回，冲突与断线保留脏稿 |
| 使用真 PTY 并断线恢复；M4/M8 / J4 | 用户明确要求；固定版本 DSH PTY 基线 | command/exec、新 shell 或错误 owner 是否被当成原终端 | 原 owner 存活时恢复同进程，输入不重放，手机控制键可用 |
| 退后台收通知、认证后返回原请求；M6 / N3、N4 | 用户明确要求；离开后继续工作必需 | 前台 toast、投递 API 成功是否被当成系统通知 | 实际后台收到并打开确切目标；旧请求按真实终态显示 |
| 真实手机输入、取消菜单后继续；M8 / C2、K4 | 用户明确要求；原生输入体验基线 | 390 px 模拟是否被当成实际键盘；按钮可见是否被当成可用 | IME 不误发送，菜单/发送可达，草稿、光标和阅读位置保留 |
| 当前过程、正常正文和结果各自可读；M5 / F1–F4 | 用户明确要求；已批准原生分组策略 | 普通说明是否被错误归为工具事件；历史图片是否被过程吞掉 | 当前展开、历史收起且尊重手动意图；结果、请求、错误可达 |
| 离开后新增大量事件，重开直接读目标视窗；M7a / L1–L4 | 用户明确要求；正常远程阅读目标必需 | 保存的末尾是否仍是当前末尾；副本追赶是否被错当成窗口就绪条件 | 默认 latest 取 N 条；显式旧位置/搜索走 around；首屏工作量与新增事件数脱钩，写入仍正确对账 |

### 2.2 审查清单，而不只检查是否照单实现

开工时从原目标写一条完整用户路径，再和要求表对照。逐项找四类问题：必要行为没有条目；条目互相矛盾；依赖或能力假设没有依据；范围被错误扩张。再从“取消、失败、离开、回来”和一个共享入口反查，尤其检查菜单、文件页、通知和迁移恢复是否缺少后半程。

具体做法是先暂时放下模块目录和旧清单，从“用户想完成什么”写出正常使用、离开后返回、失败后继续以及一个相邻功能组合。每个跨层切片至少核对一项会改变方案的关键假设：写出依据和可推翻它的场景；已有同类记录可复用，不为数量凑例子。例如“缓存标记没有后页，因此仍是最新”应被“关闭后源新增大量事件”推翻。A1–P4 和 DAG 是当前已知任务，不能定义所有可能的合格行为。

关键假设用一句话记录 `假设 → 依据 → 反例场景 → 实际观察 → 保留/修正 → 受影响任务`。先发现新反例时，回到其假设与契约更新任务和验收，不只在原实现上打补丁。必要的正常产品行为由 Agent 从原生基线、目标和源码推导，不把这项责任改成逐项向用户提问。

本计划已有的高风险假设也要复核：文件/PTY/通知分别由谁提供；未加载、未授权与未接入是否混淆；HAPI 退出后相关通用能力是否仍有承接方。固定版本的源码能确认契约，运行证据确认接通，二者分开记录。格式校验和条目计数只能发现缺行，不能证明需求完整。

发现必要缺口，由主 Agent 补入同一行为表并继续既有目标；更改不适用判定时保留原依据和新证据。只有实际产品取舍或超出授权的具体动作才形成问题：先查已有上下文、源码和批准，给出推荐及未决影响，再集中询问一次。包级批准记录包、契约、范围和原批准位置；后续在同范围内直接复用，不能以“计划又改版”为由重新索取。

需求审查的结束条件是本轮发现项均有处理结果、必要依赖均有承担者，剩余未决项明确影响哪条行为。它不要求用户逐行批准，也不宣称已证明没有任何遗漏。

## 3. 独立查漏：什么任务必须做，怎样避免共享盲区

### 3.1 触发条件与责任

下列任一情况触发独立上下文审阅：一次能力贯穿输入、源执行和展示/恢复等多个责任边界；更改共享 provider、SessionBinding、原生扩展或迁移/所有权；同一工作流被用户连续补报关联缺口。M0 退役迁移、M2–M6 的跨层交付以及 M7a 重开策略属于该范围。只有局部文案、间距或已明确边界的小修，可由实现者先放下 diff，再从用户目标审阅。

主 Agent 负责准备材料、指定审阅者并结算结论；实现者负责修复和证据；独立审阅者负责寻找未列入计划的必要行为、空壳入口和邻近回退。用户不承担补清单、代测或批准每个普通修复的职责。

独立上下文可以是已获授权的审阅子代理或另一执行会话，首轮不继承实现者的成功总结。本规范不单独授予启动代理的权限；执行时按所在环境的委派规则使用已经允许的能力。暂时没有这种上下文时可先做同 Agent 审阅并继续实现，记录其局限，安排条件具备后的独立审阅；不能把重写一段提示词称作已经独立评估，也不能删掉触发任务的审阅责任。

### 3.2 两次输入，一份结论

首轮只给原始用户目标、真正约束范围的用户决定、固定原生基线、版本/环境，以及未经“全部通过”总结的页面、操作和源端结果。实现者自己提出的架构、任务拆分及成功总结不作为首轮验收清单；已有用户批准的设计保留约束，同时允许指出它与真实目标冲突的证据。审阅者先写应有行为、组合场景和疑点，可查源码与公开契约寻找正常入口。保存首轮结果后，再提供 diff、行为表和测试记录，核对遗漏、错误假设及证据不足的完成声明。

首轮必须回答本切片对应的用户问题，例如“回来应该先看到哪里、需要等什么”“文件改完如何确认并回到任务”“菜单取消后还能否继续输入”。记录至少一条针对关键假设的可执行挑战；挑战未发现缺陷也保留实际范围，不要求强行找 bug。审阅者不能只逐项复述实现者已经通过的测试。

审阅输出沿用现有行为/问题 ID，每条包含目标依据、入口与状态、实际/期望结果、证据、用户影响，以及“确认问题／疑点待核实／无证据或不适用”。没有发现问题也要写实际审阅范围；不以挑出问题的数量衡量审阅者。

若审阅者看到按钮失效、遮挡或来源不对，先记录原路径；绕行取得结果不关闭原路径问题。工具故障和产品故障分开核实。截图怀疑不能直接变成已定位根因；复用 UI 方案的几何、操作、看图和源端证据。

### 3.3 怎样结束，而不是无限循环

默认一次完整查漏，修复后仅复核发现项和实际受影响的相邻路径。出现新的范围变化、共享契约变化或证据矛盾时，说明理由再扩审。审阅上下文优先复用既有运行材料，需要补操作时并入同一发布预算，不各自再跑一套浏览器场景。

主 Agent 对每条发现记录“确认并修复、证据不足需核实、不适用且有依据”；分歧回到原目标和可观察结果，不投票、不自动接受审阅者建议。误报保留在方法评估记录。经确认的必要行为未完成，或必须的证据未取得，该切片保持部分完成；独立可用且已经验证的修复仍按既有规则发布。

## 4. 长任务只维护一份执行记录

开始实施时在 `docs/verification/` 建立本次执行记录；已有对应文件就继续维护，不另起同义清单。主计划只链接记录并维护范围；UI 检查、独立审阅和交接都引用同一行为 ID。私密源身份、截图内容和凭据不入公共文档；证据路径按既有访问范围保存。

下面是记录格式，实施时填写实际内容。本轮不创建伪执行结果。

```text
目标与边界：原请求/主计划版本；三条原生路径；本次切片和整体剩余范围
决定与授权：决定 ID、原消息或文档位置、适用包/契约、已批准/尚需处理及原因
代码与环境：工作区提交及未提交改动范围；DSH/源版本；组件/合成/生产/真机边界
行为：ID → 用户动作与结果 → 依据类型和链接 → M/A/R 归属 → 实现责任
假设：用户决定/已验证事实/待验证设计分别列；关键假设 → 反例 → 观察 → 受影响节点
状态：实现=未做/部分/已接通/不适用；验证=通过/失败/未执行/不适用及依据
证据：实际入口与状态 → 操作 → 观察结果；文件/报告位置；版本、时间和适用范围
UI：已进入的二级页面；已查看截图及具体判断；未查入口与状态
查漏：触发理由、审阅上下文、首轮独立结果、对照差集、处理和复验
组合与异常：实际进入的状态组合；绕行前的原失败；被否定的假设及需要复核的旧证据
问题：发现者与时点；实际/期望；影响；根因是否确认；修复或保留原因
未决工作：阻断的用户行为、缺少条件、当前承担者、下一步
方法观察：首次交付时点、遗漏/复发/回退/重复确认、耗时、误报，见第 6 节
并发安排：各任务的完整行为、独占写入文件、共享契约负责人、依赖与当前状态
验证安排：选测文件与原因、稳定代码范围、通过结果的适用版本、统一发布负责人
效率观察：实际交付耗时；重复验证、等待和集成返工；可取得的总 token/API 成本
续接：最近有效结论；正在执行的命令/任务及检查方法；下一项具体动作
```

实现状态与验证状态分开，避免“未测”被写成“没实现”，也避免有代码就报通过。总结果按主计划八项用户结果和所有适用行为判断；“不适用”必须有能力、平台或已决定范围的依据，不能用来收掉难做的任务。

在关键决定、验收结果、阻塞变化、阶段交付和上下文切换前更新记录。接手者先读目标/决定/续接，核对当前 diff、运行任务和证据是否仍匹配，再继续未完成项；原 Agent 的设计判断不能因写进交接就升级成用户决定或已验证事实。新反例推翻假设时，只复核受影响的任务与证据，不从头重读全部代码或历史。版本、路径或环境已变的结果标为需要重验；未受影响且仍有效的结果复用。

证据文件应放在已有持久验证目录或报告资产目录。临时目录七天清理前，将仍用于交付判定的必要材料迁入合适位置；私密材料维持原访问边界，不为公开链接复制用户数据。交接不得只剩一个已经失效的临时截图路径。

## 5. 同时约束 Agent 的说明和界面的过程呈现

### 5.1 普通说明由源行为改进

执行本计划的 Agent 从本节采用输出要求：开始时说明目标和下一步；工作中只报告新的发现、影响、决定、真实阻碍与下一步；结束时给用户结果、证据和仍未完成的行为。耗时工作仍遵守所属环境的进度更新要求。没有新结论时，用简短状态说明解释仍在做什么，不重复整张计划或把每条工具动作改写成一段正文。

对用户有用的说明例如：“已确认文件来自正确机器，正在检查断线后保存结果的恢复。”例行的“读文件、搜索符号、再次检查、开始验证”等操作流水由原生过程展示承担。用户要求完整过程、具体命令或诊断时照常提供；需要用户决策的审批和问题保持明确；普通工具失败与重试由 Agent 处理，留在过程详情。任务确实受阻或用户操作失败时，说明影响与下一步。

M5/M8 实施时核对受控源的实际说明入口：项目任务交接文档、公开支持的会话指令或源 harness 配置。选取现有受支持入口记录落点、适用源、加载时机和验证方式；遵守指令优先级，不覆盖用户设置、不要求修改模型或所有外部 Agent 的全局配置。已有会话若不会加载新要求，明确何时生效。无法控制的外部源只按真实能力记录，不能宣称已消除其啰嗦输出。

### 5.2 客户端按真实语义组织内容

客户端继续忠实保留 assistant 正文，按原生角色、类型、阶段与手动展开意图组织工具过程。当前过程展开、历史过程收起；成果、图片、计划与请求不被吞；诊断参数按需打开。不能通过任意删除普通说明、伪造消息类型或把所有过程藏起来实现“简洁”。不更改 HHPI 协议，也不在前端偷偷改源提示词。

在既有隔离验收任务中记录一次实际受控源的输出和对应默认界面，检查每段说明是否带来新的用户信息，关键结果/请求是否仍可达；固定混合消息 fixture 用于验证分组和展示，两种证据分别记录。已有真实执行可复用，不为检查写作风格单独扩成大量模型试验。提示词已配置只能证明要求已加载，不能证明所有未来输出都满足要求；实际重复问题记录实例、发生层和处理结果。

## 6. 判断方法是否减少了用户的负担

### 6.1 观察对象和基线

在下一项尚未实施、且具体缺陷未被用户逐项点明的跨层切片上前瞻试行。开始前固定目标、行为表和试行起点；首次声明该切片已交付时保存状态快照，之后新增发现继续追加，不能回改快照使遗漏消失。附件、`/`、`@`、计划和过程折叠等已知旧问题只作回放与回归材料。

从现有记录选择同类已交付任务作为描述性基线，写明版本、范围、来源数及证据差异。历史缺少耗时或用户投入数据时标“未知”，不补造数字。无需向用户索取工时表：可记录的往返、补报和重复解释从已有对话提取，无法观察的实际投入保持未知。

所有观察使用相同窗口：首次交付到随后七个日历日，期满记录期间是否有实际使用；无使用信息标为观察不足。实施试行本身不设置无人值守后台任务，也不因等待窗口而延迟已验证发布。在后续获授权的任务中回看；尚未到期或没有回看时保持待评估。一个试行只能提供案例结果，不能证明普遍效果。

### 6.2 记录哪些数，怎么解释

| 观察项 | 统一口径 | 避免错误解释 |
| --- | --- | --- |
| 首次交付遗漏 | 原目标内的必要行为，在首次交付后由用户首次指出的独立缺口；按根因/行为去重，并列影响 | 新需求另列；代理已经明确留为未完成的记“遗留项”，不算新发现，但仍影响整体完成 |
| 同类复发 | 曾有明确修复和验证的同类缺陷再次出现，链接原问题与新触发 | 只因文案相似不算复发；根因未明注明待核实 |
| 已有体验回退 | 修改前有证据可用、修改后确认受损的邻近行为，注明来源与界面 | 未验证的旧行为不能直接算新增回归 |
| 重复确认 | 用户已明确批准同一包/契约/动作范围，Agent 再次要求相同批准的次数 | 新的真实范围变化单列，不能用“减少确认”绕过必要授权 |
| 实际行为覆盖 | 已有对应真实入口结果证据的适用行为数 / 本切片全部适用行为数；按浏览器、源端和真机分别列 | 组件通过不填浏览器通过；新增必要行为保留版本变化；不拿比率代替未完成列表 |
| 发现来源 | Agent 开工前、实现中、独立审阅中、交付后或用户交付后发现；二级页面单列 | 未去看的页面继续记未查；高发现数不自动说明质量提高 |
| 原清单外的有效发现 | 记录原清单快照、首次发现者、证据和目标依据；确认后追加行为，追踪是否在首次交付前关闭 | 已知旧问题不能算主动新发现；条目拆细、重复报告和无依据猜测不计收益 |
| 组合使用结果与错误放行 | 记录实际组合场景、失败后是否仍被判完成，以及审查中被推翻的假设 | 场景数量不是目标；没有独立期待结果的“走了一遍”不能记成功 |
| 审阅成本与误报 | 审阅增加的实际耗时、代理执行成本（有数据才记）；已核实为误报数 / 已完成核实的报告数 | 未核实疑点不算误报或真缺陷；无问题不强制凑数 |
| 总成本和用户负担 | 从开始到首次交付及后续修复的 elapsed time，另列可观察的 Agent 工作/审阅、等待、用户补报/澄清往返 | 并行时间不简单相加；用户实际操作时长未知就保留未知，不由消息时间戳推算 |

主 Agent 在执行记录内维护这些字段，不建新指标平台。回看时一起比较缺口、回归和成本：没有用户反馈不等于零缺陷；覆盖减少也不能包装成耗时改善。若流程增加很多审阅却没有提前发现有效问题，针对实际低效步骤缩减重复材料或调整审阅输入，保留原目标与必要证据。没有预设改善百分比、强制 bug 配额或无限复审。

方法评估与产品验收分开：产品是否完成仍由主计划的行为和证据判定；这套方法是否更有效，需要后续新任务和实际使用数据。本轮只补执行规范，两者都未宣称完成。

## 8. 用短反馈推进实现，集中执行发布检查

本节落实“快速实现，不把大量时间耗在重复测试”的要求，沿用 [testing.md](testing.md) 的选择器、故障演练和发布预算。它不规定开发、测试、文档必须各占多少时间。此前讨论的 70/20/10 工时分配只是排程建议，未获研究支持，不作为门槛；Google 的同名比例描述的是测试类型构成，见第 10 节。

### 8.1 开发过程中验证当前行为

实现者完成一个可观察行为后，运行能揭露其失败的相关检查。对账、重连、文件保存和跨 Pane 状态需要明确的行为回归；布局与文案优先查看真实页面，不为可逆的小改动增加实现镜像或大块快照。新增测试说明要抓住哪种失败，已有断言足够时直接复用。

单人实施按现有规范先列选测范围，再运行。共享工作区并发时，由子代理使用 `npm run test:changed -- --files <负责的路径> --list` 检查选择原因，再对相同路径执行选测，或运行对应具名行为用例；不能每个代理都扫描全部工作区 diff，反复验证其他人的修改。配置、依赖、公共契约及无法确定影响面的变化由主代理协调扩大范围，不能用窄选测覆盖它们。

UI 负责人随实现进入受影响的菜单、弹层、错误状态和返回路径，实际看图并处理发现的问题；复用同一批运行证据。真实手机键盘、后台通知和原生执行仍按主计划取得相应证据，DOM 通过不代替实际体验，也不为每个子代理另开整套浏览器流程。

### 8.2 每个可发布批次由一个负责人收尾

子代理交付代码、局部检查及未解决问题，不分别跑全量测试、构建或部署。各路径负责人接通入口和源操作，主代理在交付事件后审阅并安排发布，形成可独立发布的批次；无需等全部 M0–M8 结束才交付。

截至本次核对，[发布脚本](../scripts/deploy.mjs)已经执行类型检查、全量测试、故障演练、对应构建和发布验证；[package.json](../package.json)中的 `test:release` 又调用 `check`。准备直接发布时选用这一完整入口，避免例行串联 `check → test:release → deploy`，重复执行相同检查。独立 CI 仍执行自己的必要检查；本方案不增加跳过发布保护的参数，不修改测试脚本。

验证期间保持所检查的代码和共享依赖稳定。主代理统一安排短暂写入暂停；通过后若又合入修改，按实际影响重新检查，不能把合入前结果算给合入后版本。没有新增修改、失败或尚未解决的具体风险时停止扩大验证。失败先定位，修复后复验受影响行为，不靠重试到绿或延长预算交付。

性能检查、共享服务操作、浏览器发布场景与正式部署统一串行安排，避免争用制造假失败。现有阶段超时、浏览器场景上限、认证、原生执行和回退保护保持；真机的拟新增验收仍按主计划第 8 节处理。本轮纯文档改动只检查内容、链接和差异。

## 9. Codex subagents 按依赖和写入归属并发实施

额度中断后的执行修订以[减少重复验证与完整路径交付](development-profile-rsi.md#减少重复验证与完整路径交付)为准。目前只维护计划和 harness，产品实施暂停。后续派发按完整用户路径组织，细粒度 DAG 仍用于依赖和文件归属；模块任务完成不等于用户路径已交付。

这里使用用户指定的 Codex 原生 subagents，不改用 DSH subagent。方案从一个主代理加最多三个子代理开始，适配本次环境的四个并发名额；实施时再核对实际可用名额。它是初始安排，不是研究证明的最优代理数。本节记录后续编排方式，本轮没有启动实施代理。

具体节点与边以[开发任务 DAG](hhpi-development-dag.md)和[JSON 数据](hhpi-development-dag.json)为准。图已把组件开发与实际接通分开，逐项记录输入条件、文件写入集合、验证和外部条件。按就绪队列动态派发；以下角色表只是初始上下文分组，不能当作固定代理岗位或阶段等待点。

### 9.1 任务分组与公共代码的责任

同一组承担从入口到源端结果、展示、恢复和返回的完整动作。紧密依赖的文件交给同一代理，不能机械地拆成前端、后端、测试三队。下面是初始职责，派发前还需落实到精确文件清单；共享文件不能同时归属两个任务。

| 负责人 | 初始交付范围 | 集成责任 |
| --- | --- | --- |
| 主代理 | M1/M2 的最小共享接口、来源路由和持久操作基础；公共注册、依赖和发布入口 | 持有共享文件写入权；按派工、跨路径冲突与交付事件介入，其他时间等待；负责 M0 最终退出核对、M7 性能与历史修复、发布及总范围结算 |
| 子代理 A | M3 创建、分支、设置、队列和计划；M5 审批、提问与结果展示 | 每次交付一条完整任务流程，使用主代理已明确的接口，包含相关二级 UI 和局部验证 |
| 子代理 B | M4 源文件、编辑保存、附件与 PTY | 资源契约就绪后文件和终端分别领取；有空闲名额且文件不冲突时可并行，不把文件编辑完成当作终端前置条件 |
| 子代理 C | M6 通知、已读、后台恢复与更新返回 | 交付事件到用户实际返回的完整路径，包含权限变化、旧请求和异常恢复 |
| 各功能负责人 | 所属 M0 旧路径退出和 M8 主动 UI 检查 | 替代可用后迁移并删除对应旧实现；主代理最终检查 R1–R10、A1–P4、注册、依赖和生产产物，防止清理遗漏 |

M1/M2 先提供当前动作需要的最小契约，不先搭完整通用框架。无共享依赖的任务立即开始；其余任务在对应接口就绪后开始，不设置“所有接口全部完成”或“所有子代理全部返回”的统一等待点。暂缺依赖时报告所需契约并推进可独立部分，不能臆造另一套接口后留给主代理返工。

### 9.2 共享工作区怎样避免相互覆盖

按用户现有规则，本轮不自动建立 worktree。共享 checkout 采用唯一文件写入负责人；新增文件、公共类型、组合根、依赖及锁文件都先确认归属。子代理需要改公共文件时把具体需求交给主代理，或由主代理明确移交后再写。发生交叉修改时串行处理或合并任务，不依靠最后一次写入覆盖前者。

任务的临时产物、报告和测试端口分别归属，临时文件使用 `/mnt/cache/data-cache`。共享服务、正式发布和全量检查由主代理协调。即使文件不重叠，测试也可能读取仍在变化的共享依赖；开始验证前确认相关写入已暂停，结果记录对应代码范围。

这些约定不等同于物理工作区隔离。第 10 节的 CAID 研究显示口头约定共享工作区存在局限；这里遵守项目的 worktree 限制，并通过减少写入重叠及串行集成控制风险，不据此保证不会发生冲突。

### 9.3 派发、收取和审阅

主代理沿用第 4 节的一份执行记录，每个任务只增加一份简短任务说明：

```text
用户结果：要完成的动作、适用来源、正常及失败后的可观察结果
范围：M/A/R 条目、独占写入文件；共享契约与负责人；既有批准及约束
依赖：已可使用的接口；仍等待的具体条件；可以先完成的部分
验证：相关路径或具名用例；UI/源端需要的证据；共享资源安排
复用：已有检查及适用的代码、环境；本次新增修改需要补查的行为
交付：实际改动文件、完成行为、运行命令与结果、仍未解决项
```

子代理负责实现、入口接通和对应路径验证，不只交局部接口；开发中的组件任务可以单独结束，不要求每个都重复完整路径。路径负责人完成集成，复用子代理仍适用的检查结果。返回结果以 diff、行为和必要证据为主，不重复抄录全部日志。接手已有任务继续原上下文，不重新全量阅读源码或复做调查。

派发前同时检查硬依赖、唯一写入归属、共享资源和实际条件。完成一个节点后立即重算可运行集合；有能力接手的空闲代理可跨原分组领取任务。契约检查与 fixture 只能关闭对应组件节点，不能关闭真实接通节点。退役 manifest 未列到确切文件时不放行删除，原生执行 owner 未结算时不放行对应来源切换。

独立查漏沿用第 3 节。实施名额释放后，可安排未参与相应实现的独立上下文只读审阅；审阅者复用证据，发现具体缺口才补查，不能各跑一遍全量测试和部署。首轮输入仍不带实现者的成功总结。不为了维持代理数量，常驻一组只生成审阅报告的代理。

### 9.4 用实际交付耗时调整并发

在第 4 节同一记录中保留开始实施、依赖就绪、完成交付的时点；另列重复验证、等待和集成返工，以及可取得的总 token/API 成本。并行时段不简单相加，不拿工具调用次数、测试数量或同时在线的代理数证明加速。没有可比单代理基线时，只报告实际耗时和观察到的浪费，不声称达到某个加速倍数。

若两个任务反复等待彼此接口、修改同一组文件，或集成成本超过并行节省，主代理将它们合并或串行；若任务没有独立实现内容，不为凑并发另派代理。调整只涉及执行安排，不减少交付范围。复用现有选择器、记录和原生委派能力，不为本计划先开发新的调度器或测试平台。

## 10. 快速验证与并发实施的新增文献依据

核查日期：2026-11-07。承接本轮对两个问题的定向调研，阅读范围包括相关方法、实验结果及限制；不是系统综述。三篇 2026 年多代理论文按预印本使用，没有核实正式同行评审发表。下表区分研究结果、官方工程指导与本项目推论；不存在“AI 开发应把测试固定控制在 20%”或“开三个代理必然快三倍”的文献结论。

核查日期：2026-11-07。本轮针对“源码读过、计划审过、测试通过，仍漏掉基本产品行为”阅读原始论文的方法、案例与局限；属于定向调研。下面的研究定位行为与工作流问题，不证明当前模型的具体训练成因。`paper-lookup` 的 arXiv API 当次遭遇 TLS 错误，改从论文原站和作者工程报告核对。
