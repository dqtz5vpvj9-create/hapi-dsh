# 可复用的开发经验

适用范围：多代理、共享工作区、需要构建扩展并验证真实用户流程的开发。2026-11-08 将本轮 profile 揭示的问题直接修进执行脚本；用户随后恢复完整 HHPI 产品交付，以下约束继续应用于实际开发。历史数据见 [效率复盘](hhpi-efficiency-retrospective-2026-11-07.md)，执行入口见 [profile 规则](development-profile-rsi.md)。

## 工作怎么分

1. **交付单位是一条用户路径。** 派工包含实际入口、源端操作、结果展示和离开/失败后的恢复。一个负责人贯通并验证；组件完成另记，不由 root 在最后重新接线。先跑最短路径，再补细节。
2. **共享文件只有一个写入者。** 按依赖并发；提供目标、相关文件、接口和已有证据。对子代理使用独立简短上下文，不复制长会话和全局清单。
3. **root 按事件介入。** 完成分工后做自己的独立任务；只剩子代理工作时进入原生等待。完成、真实阻塞、共享接口冲突才重新介入。一份结果只收取、审阅一次，不让 root 重做子代理的实现和全部验证。
4. **能力边界从入口倒推。** 菜单、二级页、返回、断线、刷新与恢复属于路径。先实际点到入口，避免“第 140 分钟模块完成，第 471 分钟才发现页面漏接”。
5. **跨 Host 修复先核实际安装图。** 源 API 返回可写，不代表该 Host 的浏览器图已经装入 source provider。先复用实际 bootstrap 与目录结果，确认原生记录进入客户端，再构造路由 fixture；不能手工注入完整 Host/目录后，把通过结果当作安装链已接通。安装改动沿正式 profile 的链接目录解析，不以归档内文件存在代替安装后可加载。新接通的 provider 分支应在真实 Context 下完成消费组件初始化，覆盖公开服务及 namespace 注入；复用同一反例核对普通 Host，不把每个漏依赖留到下一轮发布后发现。Windows 同会话只读故障曾先后暴露漏装 provider、链接目录解析错误和 UI 消费分支漏注入，见[实际故障记录](../artifacts/development/hhpi-delivery-20261107/windows-original-host-readonly-20261109.md)。

6. **接入未完成不等于来源不支持。** 用户在原客户端已能完成的操作，先核对同一源的实际能力与同版原生操作语义。HHPI 的硬编码禁用、缺少单一原子 API，不能作为功能完成的依据。需要多步操作时由原源 owner 和已有持久回执处理竞争、不确定结果与恢复，界面保留用户的内容；不能把内部接线缺口包装成能力限制。2026-11-09 队列补报已据此撤回 E2 完成交付判断，恢复实际插话和附件编辑任务。
7. **首帧呈现与实际准备共用可见性策略。** 窄窗格从入口就只准备当前 Pane；不能先取得全部会话引用，再由 React 隐藏。此次 compact 修复把启动骨架、正式 UI 与 controller 接到同一策略，保留已打开引用、布局和草稿。旧版五列骨架与四个首次 retain 的具体反例已用于同一小范围回归，[修复与发布证据](../artifacts/development/hhpi-delivery-20261107/R0-compact-worker-published-20261109.md)复用，不再按设备复制功能任务。
8. **恢复必须让用户继续操作。** “原文还在”和“没有重复发送”不能代替恢复完成。检查原进程中断或轮次结束后，同一个原生按钮是否仍能继续；已确认交接给后继记录后，旧记录不能再次出现在界面。本轮队列审查分别发现未尝试步骤永久等待、idle 时入口仍被禁用，以及恢复后再次插话重复显示；沿同一实际状态转换补最小反例，不另建设备或通用异常矩阵。见[队列修复记录](../artifacts/development/hhpi-delivery-20261107/native-queue-controls-20261109.json)。

## 确定性工作怎么跑

- 使用仓库入口完成类型检查、源准备、扩展构建与安装；同样输入的执行合并和复用由普通进程完成，模型不轮询等待。
- **只读探针保留真实初始化读取。** 读取白名单按当前已安装契约核对，包括必要的只读 stream；记录被拦截的方法。初始化读取被探针拒绝时，先区分探针阻断与产品故障，再做有明确修正理由的续验，保留原失败，不原样延长等待或重新构建产品。
- **身份依据内容。** 输入身份包含源文件、依赖、配置和工具链；HEAD 不代表带未提交修改的工作区。同名包、相同版本号也不代表相同产物。
- **冻结身份先于编译。** 客户端增量先完成实际 copy manifest 和 after hash 确认，再请求编译；copy 失败立即停止依赖步骤，输入字节未变就不请求 build。正式扩展构建沿[已有命令模板](hhpi-extension-install.md#从源码准备构建和安装)传入 `--expected-source` 的 prepare 输出或已验证冻结清单，开工前核对 prepared 的 top/native 来源；有整树 hash 才核对整树，不能事后猜写 metadata。`.17` 曾在 290.888 秒编译后才发现仍携带 `.16` 来源，随后复用编译重 pack 108.745 秒；该失败与恢复历史保留，不把新检查追认成旧构建 recipe。
- **缓存依据实际输出。** 只有成功且输入仍匹配、所需产物仍存在且完整时才复用。丢失、损坏、输入在执行中变化、上次失败都不能写成成功缓存。
- **增量与发布一致性并存。** 保留依赖环境和编译增量状态，重建受影响内容；最终扩展集合仍必须完整、版本与来源一致。发布和其他副作用不能只凭“上次通过”跳过。
- **升级复用可信 runtime 锁。** 正式安装器从当前 profile 的已激活 release 核对 bundle、runtime seal、输入、pnpm 版本及已安装锁副本后，只为无锁的新 runtime 继承 `pnpm-lock.yaml`；已有目标锁保留。不复制 `node_modules`，条件不符就走原安装流程。随后仍由 pnpm 更新新 `file:` payload 和依赖，离线模式由实际安装调用选择。无需再手工找到上一 runtime 并复制锁来避开无关依赖的重新解析。
- **安装调用使用实际包管理器。** 从各 active runtime 的 `.modules.yaml` 核对 pnpm 版本，再选择对应的正式入口。此次中央使用 11.22.0，两台 Windows 使用 11.28.5；不能把 SDK builder 的版本直接当作所有消费者的版本。需要离线安装时显式传 `--offline`，不假定环境变量会被该版本采用。中央首次版本不符而回退联网的失败已保留，随后沿正式安装器复用可信锁完成升级，没有手搬锁或更改 TLS。
- **切换前采齐同批次空闲证据。** 在发布锁内先读各 Host/Runner 的权威执行状态，再切中央与 Runner。严格 cohort 校验会使旧 Runner 暂时无法通过新中央读取；这不能反推它仍在执行。若切换中需要补证，以原 PID/启动时间、已关闭的入站通道、官方写 lease 和最新执行记录核对连续性，不能绕认证或启动替代 owner。
- **文件归属只计算一次。** 构建依赖图先把源文件分到最近的包或全局输入，再计算各包及依赖闭包的签名；不要为每个包重扫全部文件并再次查找所属包。本轮 395 个 workspace 的重复扫描在实际构建中造成数分钟的前处理，修复后单独图构建为 8.529 秒；该测量不包含完整编译，也不作为其他机器的耗时承诺。
- **一次带回完整诊断。** 批量处理同一轮错误后再查；连续相同失败先定位原因，再改变方法。相同输入的并发请求共享成功或失败，不各自再跑一份。
- **验证覆盖本次变化。** 内循环跑相关行为，整合后复用适用证据。只在代码、环境、失败或未覆盖风险变化时重跑；发布既有保护保留。夹具、真实编译器、上游构建、浏览器、真机分别记录。
- **延迟加载功能从实际安装入口检查。** 内层组件通过不能说明入口未加载、面板关闭或重挂载时仍正确。涉及共享恢复状态时，把实际注册入口与其共同使用方放在同一个针对性用例中；先检查内容是否可达、是否重复展示、是否仍属于原账号与会话。只补本次遗漏的边界，复用未变的内层行为证据。
- **旧数据离开当前窗口也属于正常恢复。** 实际检查发现“旧消息已在正文，但待发项等不到它重新显示”时，先核对生产恢复逻辑，不能直接归为夹具太旧。当前发送与重开后的已消费旧项分别判断：前者保持到正文接管，后者沿同源送达证据和官方已提交窗口结算；首次查询失败应能沿既有重连事件恢复。只补同一路径的反例，复用已通过的画面和操作结果，不另造模型任务或全量回归。[本次缺陷与修复证据](../artifacts/development/hhpi-delivery-20261107/native-queue-controls-20261109.md)。
- **先核对验收输入。** 正式用户路径开始前核对实际 Host、客户端与扩展内容；线上热修复版可能不含待交付的完整改动。已有浏览器、设备、CA和隔离环境可继续复用，只更换需要验证的版本。
- **区分模块 revision 与内容。** 当前官方 `client-modules` 的 `artifactRevision` 来自文件的 mtime、ctime 和大小，不是内容 hash。同一产物在 stage 与安装目录中可以有不同 revision；跨目录一致性沿用正式 payload SHA 和实际服务字节核对，不能只因 revision 不同就重建。此次 `.14` 的 stage `41d9/95e2` 与生产 `d032/c3b9` 对应相同客户端字节。
- **操作具体的可见 Pane。** 先用 canonical session 和实际可见状态锁定原聊天，再在该 Pane 内找输入和菜单；文件页沿这次导航得到的 Pane 或准确文件路径继续定位。已知精确会话的存在与能力以其 `resolve/read` 为准，冷目录尚未列出它只影响列表准备，验收脚本不据此拒绝该目标。工作区保留的隐藏图也可能有同名输入，不能用全局 `.first()` 代替目标身份。Files 与 M4 检查曾因此命中隐藏的 Choose workspace，未到用户操作就超时；这类结果不算产品复现。
- **脚本路径不决定工作目录。** 构建私有发布包时，命令的 `workdir` 必须是该包目录；绝对 `build-client.mjs` 路径仍会按当前目录解析入口并写入 `dist`。M4 曾从根仓库误生成 Client，已排除该产物，随后在私有 `.8` package 目录完成匹配构建；不为修正生成物再跑无关全量构建。

## profile 怎么解释

- 按工作目的记录 `product-test`、`typecheck`、`install`、`generate`、`build`；并发、嵌套不会把它们变成 verification。类别同时给并集和累计，跨类别时间不能直接相加。
- 命令继承实际 agent 和 parent；缺失身份记未归属。逐响应用量按 response ID 去重，输入、缓存和输出分开。不能据此推算 Pro 周额度。
- 轮次窗口、推理条目生命周期、命令时长和服务存活是四个不同对象。推理条目可能包含等待；不知道的时间保留未知。经证据确认的后台服务和隧道排除出工作覆盖，原始记录仍保留。
- 采集器按字节游标增量读取；任务上下文只读取当前节点证据。看板在新记录或心跳时更新，不每两秒重算完整历史。
- RSI 对照已取消，CLI 和底层执行函数均停止启动 worker。直接在真实开发中改进脚本，保留历史负结果；本机脚本测试不冒充模型能力实验。
- 新发现的实际用户路径可直接登记有证据的成功，不需要编造一条失败来解锁记录。新增项保留追加标记，不能顶替原清单中的未验证要求。

## 交付时说什么

返回改动、已走通的路径、复用证据、仍未验证的边界。编译与测试通过支持各自断言，不自动等于产品完成。普通命令失败和重试留在原生过程详情；只有任务受影响、需要用户操作的问题才进入正文。

本轮实际验收结果由同页末尾记录。每次后续采用这些方法，更新对应工作记录即可，不另开一轮方法论项目。
