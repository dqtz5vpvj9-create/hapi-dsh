## 3. P0-A：加载慢的完整诊断与架构 A

### 3.1 真实站点实测（fresh browser context，恢复 13 pane 布局）

- `[data-hapi-workspace]` 可见：**17.41s**。
- Root graph：58 个 plugin/bootstrap 响应，841→8379ms，span 7.5s（localhost HTTP，官方 Loader 每 row 一个资源）。开头 3 个是 combo，后续行请求混在同一 bucket，不能简单说 root 全部 58 个。
- 远端 Host A：47 个响应，6364→15587ms（bootstrap + plugin rows 经 Hub 隧道，成波次）。
- 远端 Host B：13 个响应，6379→12398ms。
- 每个远端 Host 在启动过程中被 bootstrap 两次（catalog graph 一次、pane/刷新一次）。
- 12s 时仍有 5 个 pane loading；13 个 pane 已知。
- 已经 warm 的本地会话点击→conversation scroll 可见：**279ms**（说明问题在冷启动与 attach，不在会话切换本身；但 279ms 是元素可见时间，不必然等于完整正文读齐）。
- HAPI 参考：document + 1 个主 JS + 1 个 vendor JS + 3 个 CSS；全局 SSE + message-window-store + tail cache，无 per-session bundle graph。

### 3.2 架构对比（核心结论）

| 维度 | HAPI | hapi-dsh 现状 |
|---|---|---|
| 前端实例 | 1 个 SPA，所有会话共用 | root graph + 每 Host catalog graph + 每 pane 官方 Client graph |
| 冷启动资源 | 1 主 JS + 1 vendor JS + 3 CSS | root 58 个 plugin 资源；每 Host ~54 个；远端全部过隧道 |
| 会话打开 | tail cache 立即渲染 + 有界 refresh | 先阻塞读完整 native history，再 attach live |
| 实时 | 全局 SSE；message-received/updated 增量 ingest；streamSnapshot 按 streamId 合并 | 每 pane 独立订阅；history 成功后才接 live |
| 历史/live | window store 按序合并，live 不被历史覆盖 | 两阶段，history 失败回退 cache，产生缺口 |
| 预热/缓存 | 最近 5 会话 warmup；SPA 天生缓存 | 无会话预热；只共享编译 wrapper，无持久 bundle 缓存 |
| 传输 | 同源静态资源 | 远端资源经 Hub 反隧道，chunk ACK + base64 |

根因归纳：
1. 官方 DSH 假设“一个 Host 一个 App 实例”，我们按 pane/Host 实例化 N 次，每次都要 bootstrap + Loader + Context + service activation。
2. 官方 graph 的 bundle 粒度（单 row 资源）在隧道上被放大；每个远端 Host ~54 个请求、两次 bootstrap。
3. Root shell 自身很重：workspace 可见前要等 root graph 58 个资源 + 多层激活。
4. 没有 HAPI 式 tail store / 会话 warmup / live-first attach；打开历史是阻塞的。
5. 恢复布局同时启动多个 pane/Host；lazy 只推迟 parked 窗口，没有资源级调度。
6. 缓存只到编译层；fetch/activation/bootstrap/session seed 无复用。
7. 我们没有利用官方可能已有的多窗格/多 session view 能力（待验证，见 3.4）。

### 3.3 架构 A（已拍板）

**目标**：每个 Host（本地 Host + 每个远端 Host）只创建一个官方 Client graph；pane 是这个 graph 内的 session view。删掉“每 pane 一个新 graph / 每 pane 一份 cold boot”。

预期收益：
- 每 Host 的资源加载/激活只发生一次（远端只过一次 54-row 冷启动，之后会话点击是 bind）。
- 本地/HAPI source 会话复用主 Host graph，可完全去掉 per-pane graph。
- live stream 自然共享：一个 Host graph 的事件流服务所有 pane，attach 点问题消失。
- 内存从 N 份 graph 降到每 Host 一份 + 每 session view 的增量。

## 4. P0-B：消息缺口 / 实时连续性

### 4.1 证据

- 用户截图的会话（session `b197ad63-…`，Codex native）源历史里两条都在：`昨天你打包为 GZ…` native seq 358320001（08:31:02 北京时间）、`文件哈希校验过了对吧？` seq 358850001（08:34:14）。
- 当前线上重新打开该会话：DOM 初始窗口同时包含两条；向上滚后 transcript 从 2440 扩展到 9776 字符。**源数据没有丢，当前渲染也没有丢。**
- 因此“漏一条”是打开/attach 时机的 transient：先阻塞读 history，读完才 attach live；若打开时 Codex 正在流式输出，epoch 变化会让 epoch-stable pass 在 4 次尝试后失败，回退到 `cache.read()` 旧快照；live 从当前点追加，cache 末尾到 attach 点之间形成真实缺口。刷新后（流稳定、history 完整）恢复。
- 另一个观感来源：官方 Conversation 初始窗口按 turn 边界截断，较早一轮在窗口外，看起来像漏消息（向上滚动/加载更早可恢复）。

### 4.2 HAPI 的做法（应作为目标）

- `web/src/lib/recent-session-warmup.ts`：全局 SSE、最近 5 个会话 warmup、tail cache；打开 `openMessageTailFromCache()`。
- `web/src/chat/reducerTimeline.ts:835-920`：`streamSnapshot` 按 `streamId` 原地合并文本/reasoning block；`message-received`/`message-updated` 持续 ingest。
- 历史页与 live 尾在 message-window-store 合并；live 永不回退覆盖。

### 4.3 修复要求

1. 打开会话先订阅/缓冲 live，再异步 backfill 历史；首屏用 graph journal/tail 或最近缓存。
2. 历史与 live 按 seq/localId 合并；epoch 变化保留与 live 重叠的连续后缀，不整段重来、不回退旧 cache。
3. Host 侧维护 append-only 每会话 tail journal（现有 delivery/journal 机制可借鉴），刷新/重开不重读整段 Codex history。
4. 像 HAPI 一样 warm 最近会话（tail + 事件）。
5. cache fallback 必须显式 stale + attach 后对账补读，禁止静默接上。
6. 初始窗口：打开时预取上一页（复用 seamless 的加载能力），避免“上一轮在窗口外”被当成丢消息。
7. 测试：活动会话打开/刷新、epoch churn、cache fallback、历史/live 重叠、不重复/不丢行。

- 远端 pane 首开仍受 Hub 隧道影响；prefetch 会形成 maxQueued≈51 的 enqueue 突发（wire 并发受限）。
- 官方 `ui-sidebar-right` 会打印 `Session reference … is released`（启动竞态日志，eager baseline 也有）。
- 官方 main panel（Plugins 等）替换 header 后没有固定“回 Conversation”入口。

- 长会话全量 seed 开窗慢是 projection/transport 层，seamless 不解决。
- 全量 Playwright 未在最近构建上重跑；发版前只跑微测试 + 定向 e2e（见 §7）。

## 8. 架构 A 的验收目标（建议写入 PR）

- 已 warm 的会话点击→正文可见：**p95 < 150ms**（元素出现与正文加载分别记录）。
- 缓存恢复首屏 transcript：**< 500ms**；冷 Host 允许受隧道 RTT 限制，但要记录冷/热两套数字。
- 每个 Host 的 bundle 请求在启动后只发生一次；恢复 13 pane 时活动窗口 ready 不再出现 17s 级延迟。
- 2/4 pane heap 不高于现状 77.8MB@4；per-pane 增量记录。
- 多 pane 独立：草稿、滚动位置、对话框、审批、focus 不串台；关闭 pane 不终止执行；单 sidebar；native thread identity/ownership 不变。
- 活动会话打开/刷新不出现缺口：live-first + backfill 测试 + 真实站点探针（打开正在输出的会话、刷新、滚动）。
- 定向 e2e：`pane-surface`、`workspace-chrome`、`composer-enter`、`native-history`、`workspace`、`source-engines`、`queued-edit` 至少这些；`workspace.spec.ts` 的 pane 几何/恢复断言要重点看。
