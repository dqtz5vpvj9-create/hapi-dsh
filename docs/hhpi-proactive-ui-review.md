# HHPI：如何主动发现 UI 错误

状态：当前 UI 开发与交付规范，2026-11-09 补齐二级面板要求。配套[HHPI 交付计划](hhpi-product-change-plan-2026-11-07.md)，具体实现和验收状态记录在各功能任务中；本规范不代表界面已合格。当前停止手机/手机视口验收与帧率调优，下文旧设备安排以主计划的最新用户指令为准。

**目标是让 Agent 在交付前主动发现用户一眼能看出的错误，也发现必须打开菜单、弹层和辅助页面才能遇到的问题。** 这需要规定去哪里看、如何操作、用什么判断、发现后怎么办。仅增加测试数量或在交付清单里写“检查 UI”，不足以达成这个目标。

本次目标以主方案第八版为准：删除 HAPI 兼容来源，最终运行路径只有本机 DSH、官方 DSH federation 与 HHPI 直连 Codex。入口盘点必须区分“退役的 HAPI 专属入口”和“仍需独立提供的工作流”：旧 Hub/Companion 页面应该消失，文件、终端、分享、通知等能力必须完整替代。历史 HAPI 截图只提供经验，不再是来源回归要求。

本文件负责怎么到达、观察和判断界面。开工时的需求审查、复杂任务的独立查漏、续接和效果评估统一执行[交付方法与记录规范](hhpi-delivery-method.md)，实际结果共用其中的执行记录。

并发实施时，各功能负责人随修改检查自己的主界面、二级入口和返回路径；主代理统一安排共享浏览器、性能检查及发布预算。审阅者复用已经取得的实际材料，发现具体缺口才补查，不各自重跑一套全产品流程。快速验证和 Codex 分工见交付方法第 8–9 节，UI 完成条件不因并发而缩减。

[开发任务 DAG](hhpi-development-dag.md)中的 V1/V2 可以在相应功能接通后提前取得真实手机与后台通知证据，不等所有退役工作结束；后续影响该路径的修改必须复验。V3 汇总此前各切片的独立查漏，不作为把 UI 检查推迟到交付末尾的理由。

主动检查还要从旧书签、恢复的 Pane、通知、分享链接和延迟菜单进入。已精确映射的入口返回原生任务；无法映射时展示明确恢复信息和已保存内容，不能发起 Hub 请求、落到错误会话、丢草稿或留下空白页。检查新装及升级两种入口，不能只验一个没有旧数据的干净工作区。

## UI 交付要求：组件、信息层级与实际画面

适用于聊天主界面和设置、队列与目标、权限、文件、终端等二级界面。由原功能负责人随实现完成，审阅证据写进同一任务，不另建手机任务或全产品复测阶段。

1. **先选原生组件。** 实施前核对 pinned DSH 已公开的按钮、输入、菜单、弹层及主题能力，记录本次复用的组件与默认状态。已有适用基础组件就直接使用；缺少专用组件时复用原生样式令牌与交互约定。出现浏览器默认按钮、边框或与原生主题失配的裸表单，不能判为交付合格。
2. **先组织用户任务。** 默认画面呈现当前对象、影响用户的状态和适用操作；修改内容时才进入编辑。详细用量、内部字段、低频操作放在已有次级入口。空状态简短说明即可。数字与时间使用可读格式，说明累计口径，不把原始秒数冒充实际工作时间。提示与异常处理遵守[默认界面与恢复状态规则](#ui-state-contract)，不逐项展示后台状态。
3. **同一路径看交互与画面。** 操作原入口、打开受影响弹层、完成或取消，再回到原内容，检查焦点和草稿。实际查看目标状态截图，判断主次、留白、长内容、遮挡、关闭/返回，以及本次涉及的禁用、选中、焦点和主题状态；按改动选取，不穷举状态组合。
4. **按证据关闭任务。** 记录组件复用、具体版本、看过的画面与判断、操作/返回结果及未验证项。已有修改前截图直接复用，新增修改后画面作比较。功能动作成功、测试通过、截图生成均不能单独关闭 UI 质量问题；信息层级或明显布局仍不合格时，留在原功能任务修复。相同输入和状态的有效验证复用，避免重复检查。

**本次“队列与目标”面板的具体要求：** 默认先展示目标正文、当前状态和源实际支持且适用于该状态的操作；编辑目标再显示表单，清除等低频动作放菜单；用量详情按需展开，数字/时间格式化；空队列一行说明，非空队列保留编辑、取消、排序和开始等适用操作；刷新与关闭归入标题栏，失效/恢复状态仍能关闭。验收包含默认画面、编辑取消、关闭与返回原草稿。既有队列/Goal 操作证据保留，视觉可用性另记，不能从此前操作成功推导面板已完成。

**发送后的连续可见性：** 在任务正在执行时，从实际输入框发送一条消息，必须在同一输入区的 DSH 原生队列 UI 中持续看到它，直到对应正文接管；文字和附件不能在收到 accepted 后先消失，再等待源历史把它补回来。核对原生 `inbox` / QueueDock 的数据与操作接入，管理面板里的队列列表不能代替它。测试预期先依据这条用户行为确定；已有断言如果把中途消失当成成功，应修正断言和实现。只补本次缺失的发送状态交接，不另建整套测试。

## 1. 先明确现有检查能发现什么

现有[测试规范](testing.md)已经区分契约、DOM、真实浏览器和物理设备，并要求 Agent 看图。这里补上主动探索与审查方法，不另建整应用 E2E 系统。

| 已有检查 | 能证明什么 | 仍可能漏掉什么 |
| --- | --- | --- |
| [设置组件用例](../tests/experience/hhpi-codex-settings.test.tsx) | 生产 controller 的确认值与 pending、特定重复点击处理、模型选择器能打开 | jsdom 没有真实布局；弹层能打开不证明没有遮挡、内容可读或手机上容易操作 |
| [原生内容浏览器用例](../tests/browser/codex-rendering-journey.mjs) | 真实官方组件的命令、Diff、图片等路径；页面/正文宽度、编辑器可见与命中 | 检查对象有限；不能由编辑器命中推导出所有菜单可用，更不能推导出信息密度合理 |
| [官方组件实验室](../tests/browser/README.md) | 固定版本的真实组件、生产投影与读取逻辑，配合声明过的合成边界 | 外壳、传输和部分源 IO 是 fixture；不能覆盖部署后的全部菜单、来源路由和权限组合 |
| [截图采集器](../scripts/test-smoke-capture.mjs) | 固定 webshot 命令得到就绪页面的图像 | 返回值仍是 `visualReview: required` 和 `interactionChecks: not-run`；工具没有替 Agent 看图或操作 |

由此不能得出“现有测试没用”。应保留已有保护，再补三类发现手段：**入口盘点、带目标的实际操作、基于截图的视觉与内容审查。** 几何检查帮助定位，不负责判断整个产品是否好用。

## 2. 从入口清单发现遗漏，不能只等页面自己出现

先用源码、公开注册和真实页面共同整理入口清单。覆盖路由、侧栏和 Pane 菜单、输入工具栏、`/`、`@`、消息动作、通知深链接、卡片和延迟加载的面板。与来源能力清单对照：某能力应有入口却完全没有入口，也是一项发现；单靠抓当前 DOM 找不到这类问题。

一行代表一个“入口 → 页面/弹层 → 结果 → 返回”的关系，最少记录：所属来源、SessionBinding、相关模块、适用状态、最近实际检查的版本及证据、未检查项。复用现有能力和文档信息，不另造一份运行时 registry，不在报告中保存生产私密内容或凭据。

每行再分开记录三件事：**是否真正进入目标状态、是否查看实际画面并形成判断、操作是否产生预期用户结果**。导航成功不能代填后两项。选择切片检查时补一个与当前修改有关、此前未覆盖的组合状态：例如菜单打开且软键盘在场、文件有脏稿且源端变化、离开后新增大量消息再通过通知返回。已有等价证据可复用，不要求全组合穷举或每次全站漫游。

对于会话重开，必须分别进入默认最新、显式继续旧位置和定点链接；用主计划 M7a 的 Δ/N 记录判断是否无谓追赶中间正文。只看到最后成功到达页面，不能证明等待过程和加载策略合理。

盘点同时标明能力提供方是 Agent 原生接口、源机器工作区服务还是应用服务。文件保存、用户终端和后台推送不因 Codex 方法表缺项就从界面清单中消失；分别检查源机器 provider、DSH PTY 与 Host 通知服务。当前未测只记未测，不先写成功能缺失；已有实现也不能自动标通过。

## 3. 何时主动查，怎么选择场景

**首次建立基线**：清单覆盖全部产品入口，逐项区分已有证据、源码疑点和未检查。已有近期证据可以复用，但必须匹配版本和行为；HAPI 截图、设计稿和旧 DSH 版本都不能当成当前 HHPI 验收。先处理已知用户痛点、主要任务路径及高风险二级页面。当前预算内没有执行的仍列为未检查，不宣称一次巡查覆盖全应用。

**每个功能切片**：从用户目标而非改动文件名确定检查范围。修附件入口自然包含选择、上传、显示、移除、提交和恢复；修分支自然包含菜单/命令入口、确切新会话、父会话返回和待确认。它们是同一目标的必要工作，不等用户再逐项要求。

**共享能力变更**：主题、全局样式、Portal、官方扩展升级、输入/SessionBinding 或来源 provider 改动，都要查共同使用方。优先选不同来源、不同 Pane 宽度和最容易拥挤的二级页面，不能只重看刚改的组件。

**每轮选取顺序**：本次受影响的关键路径 → 同一共用组件的邻近入口 → 高风险且没有近期实际检查证据的二级界面。后者从清单中选，不能总选聊天首页。若预算只容得下前者，明确留下后者，不伪造覆盖率，也不为了凑覆盖挤掉关键验证。

场景不做“所有页面 × 所有状态 × 所有来源”的全组合。每个功能选择正常路径和最可能出问题的一种变化：候选看查询竞争，文件看迟到读取，计划看回执未明，弹层看窄屏与长文本。先在契约/组件层穷尽需要的状态；浏览器只处理真实布局、集成和操作证据。

## 4. 一轮检查如何执行

<a id="ui-state-contract"></a>
### 默认界面与恢复状态规则（用户纠正，2026-11-09）

适用于所有新增或修改的提示、错误处理、保存/同步状态、发送回执及恢复界面，包括聊天、输入区、二级面板和全局通知。这是实施约束；后端可靠性机制继续保留，呈现方式由用户任务决定。

1. **先找用户要完成的动作，再决定是否展示。** 普通后台刷新、重试、已保存、回执到达等自动处理过程不增加界面元素。用户确实无法继续或需要作决定时，在相关消息或入口给出简短影响和可执行动作；仅“状态发生变化”不构成展示理由。
2. **接入现有原生位置。** 队列使用 DSH QueueDock，推理/工具沿原生过程分组，审批使用原请求组件。HHPI 负责补齐来源接入，不因适配层多了状态而自建平行面板。默认聊天正文放用户消息、结果、重要进展和必须处理的请求。
3. **消息连续可见且只有一份。** 发送后，待处理内容留在原生队列或对应的消息位置；正式正文接管后移除临时表示。编辑保留原附件/引用与身份。持久回执、保存副本和内部对账在后台处理，不生成“原执行端已保存”“附件已保留，请自行恢复”正文块，不要求用户管理内部账本。确有需恢复的未送达内容，在原消息/草稿入口提供恢复，不删除数据或盲目重发。
4. **错误按用户影响呈现。** 短暂目录刷新/连接失败保留有效正文、目录和草稿，后台恢复；持续断线用已有连接状态说明。用户触发的操作失败，在该操作处说明影响和重试方式。原始 HTTP/RPC、内部 URL、堆栈、哈希和协议错误仅供诊断，不直接作为全局红条、toast 或聊天内容。
5. **临时提示必须结束。** 实现时写清出现条件、所属会话/Pane、消失条件。读者已到达上次位置或完成定位后，“继续上次阅读”消失；队列转正文、上传完成、连接恢复等使用真实结果结束状态。不能仅靠用户关掉提示，也不能用任意定时隐藏掩盖未完成操作；另一 Pane 的状态不得误清当前提示。
6. **折叠不是内部垃圾的默认出口。** 不为每个回执、失败或重试添加新的 details、“查看原文”卡或重复摘要。必要诊断进入已有过程详情或明确的诊断入口，默认不占用聊天阅读空间。用户请求的代码、原始输出及审批所需内容照常保留。
7. **在同一功能里看默认画面和恢复终态。** 负责人在原路径内检查状态出现、操作结果和状态消失，实际看受影响画面；正文/输入可用但被重复提示挤占，也判为该路径缺陷。复用既有适用证据与同一场景，不另建设备任务、全量 UI 矩阵或额外审批流程。

实现记录只需在原任务中说明：**用户受什么影响；放在哪个已有组件；何时消失。** 自动处理且没有用户影响的状态，默认不展示。审阅不接受“用户需要知道内部发生了什么”作为新增 UI 的理由。

2026-11-09 用户截图中的具体不合格反例：

| 反例 | 必须得到的行为 |
| --- | --- |
| 顶部常驻 `transport failure for /api/hapi/catalog: HTTP …` | 查清请求失败及恢复；有效聊天保留，原始技术错误不占全局栏，恢复后已有异常状态清除 |
| 到达目标附近后“继续上次阅读 ↑”仍永久显示 | 以同一读者实际到达/完成定位为终点；仍在别处的合法旧读位入口保留 |
| 展开的“原执行端已保存 · 查看原文”再次显示状态和用户原文 | 消息在原生队列与正式正文间交接，保存回执在后台处理，没有第三份正文块 |
| 已有原生队列却把消息藏到“更多/恢复副本” | 用户直接在 QueueDock 看见并操作待处理消息，正文接管后队列项退出 |

上述截图证明呈现缺陷，具体请求失败原因和状态根因须按各任务的源码/运行证据定位；写入本规则不等于缺陷已经修复。

### 第一步：先写用户要完成的事和预期结果

例如：“我已经在 A 任务里写了草稿，要从它的文件页选一段内容带回，继续发给 A。”预期结果是文件来自 A 的机器、引用回到 A、旧草稿和阅读位置保留。先写目标，再找入口，防止测试因为知道私有 selector 而绕过难找或缺失的产品入口。

需要深链接验证时另外标明。直接打开面板内部 URL、调用 React handler、调用 provider 成功，都不能代替用户从正常菜单进入。

### 第二步：用有代表性的内容进入实际状态

使用已安装的官方 UI 和生产组件，在明确的源 RPC/文件 IO 边界设置合成数据。保留真实样式、Portal、编辑器和正常导航。若使用组件实验室的合成外壳，单独记为组件集成；整工作区接入仍需对应证据。

基础数据包含中文与英文长标题、深路径、长草稿、长截图和“过程→普通正文→新过程→计划/图片→结果”的混合内容。不要只用 `Task`、两字文件名、单行回复和已完成的空闲会话。按本次功能制造一个可控的延迟、错误或 pending，确认用户在等待时仍知道发生什么、能做什么。

生产探针只读。发送、创建、审批、取消、文件写入和断网在合成会话或隔离测试环境中执行，不为 UI 探索试点真实生产动作。

### 第三步：实际操作，同时检查几何与归属

通过可访问名称、真实点击/触摸/键盘进入菜单、弹层和下一页，取消一次，再完成一次，并回到原位置。选图要验证真实按钮能打开 chooser；直接 `setInputFiles` 只能证明后续处理，不能证明附件按钮能用。合成源需记录收到的完整目标和操作身份，不能只断言按钮变色或 RPC 返回 200。

几何检查集中在当前可见 Pane、弹层和关键控件，不逐帧遍历全部历史 DOM，也不把昂贵布局探针与性能测量混在一起。

| 检查对象 | 如何发现问题 | 判定边界 |
| --- | --- | --- |
| 页面、Pane、弹层边界 | 分别比较容器与内容范围，检查关键动作相对可见区域的位置 | 页面没有横向滚动不代表内部未裁切；`overflow:hidden` 可能只是把问题藏了起来 |
| 点击目标 | 在控件实际可点击区域检查命中，再执行真实点击看结果 | 单个中心点命中是线索；图标、子元素、遮罩和透明覆盖需结合操作判断 |
| 弹层和菜单 | 进入位于上下/左右边缘的入口，滚到底，操作最后一项、关闭和返回 | 主操作可以经正常滚动到达；不能被屏外裁掉，也不能靠缩放页面才能点到 |
| 输入区占用 | 空输入、长草稿、附件、运行状态分别观察正文还剩多少空间 | 使用已确认的紧凑两行设计作基线；不能用“编辑器可见”允许空输入框占据半屏 |
| 焦点与键盘 | 检查 Tab 顺序、可见焦点、Esc 关闭、回到原编辑位置、中文组合不误发送 | 桌面中文插入不证明 OS 输入法候选交互；viewport 缩小不证明软键盘行为 |
| 媒体与可滚动内容 | 看缩略图实际内容、原图是否能打开、代码/Diff 内滚动及返回 | 代码/Diff 内横向滚动可合理；整页被长路径撑宽或长图被裁成空白不是合理滚动 |
| 读取与更新 | 观察当前锚点、草稿、结果与源身份，再放行迟到事件 | 最终恢复正常不能掩盖中途正文消失、跳到别处或操作发给错误会话 |

360/390 CSS px 是现有移动布局检查范围；桌面还要看真实窄 Pane，而非只看 1440 px 的整个窗口。小屏关键触控区域以已批准设计及实际可用性判断，不能靠缩小字体和点击面积“通过宽度检查”。历史文档中的 98 px 输入框高度是特定版本的测量，不是所有状态必须精确相等的硬编码。

### 第四步：Agent 必须实际看图，审查内容和体验

截图用 `webshot` 的固定入口，等待**目标状态**就绪：如指定会话正文及编辑器、打开后的特定弹层、媒体加载后的预览。只等外壳或 `body` 会拍到错误状态。webshot 使用独立浏览器上下文；不能把另一个浏览器中打开过菜单当作这张图也包含菜单。需要在同一版本的隔离环境重现目标状态，并核对截图里实际出现的内容。

截图生成后必须用图像读取工具打开，按当前画面回答下面的问题，结论写出具体位置和现象。几何断言通过也照样看图。

| 判断 | 不合格的具体例子 |
| --- | --- |
| 我能否看出这是哪个任务、正在做什么、下一步是什么？ | 只显示内部 ID 或 JSON；“已接受”被写成完成；出错只说 operation invalid |
| 当前最重要的内容是否在正常阅读路径？ | 图片只剩“已调用工具”；计划有正文却没有适用动作；待审批被折叠进已完成过程 |
| 常用操作是否容易发现且够紧凑？ | 发送按钮滑到屏外；模型菜单一打开盖住所有输入；每项状态各占一行；空白比内容多 |
| 过程组织是否符合当前阶段？ | 全部历史过程默认展开，或当前工作也全部收起；正文已经出现但旧过程仍霸占屏幕 |
| 页面是否按同一套设计呈现？ | 原生卡片里突然出现浏览器默认按钮/输入边框；间距、对齐、字号、深色主题明显失配 |
| 用户是否被要求理解内部实现？ | 默认铺开 RPC 参数、重连日志、base64、重复诊断；让用户自己处理内部队列容量或协议状态 |
| 操作后能否继续？ | 预览没有明显关闭/返回；菜单取消丢光标；分支“成功”但找不到新会话；错误没有可行去路 |

这里的例子来自用户此前反馈和参考要求，**不代表本次重现了当前版本的这些问题**。在具体版本上观察到才记为当前缺陷。合法的代码、用户要求的 JSON 输出、审批所需命令和错误关键内容不能被通用“降噪”规则删掉。

对照已批准的紧凑输入设计、当前 pinned DSH 组件行为及 HAPI 中同类工作流，比较完成目标需要的操作、默认内容和返回方式；不照抄 HAPI 全部 UI，也不把旧截图作为像素模板。截图差异只能提示变化，Agent 要判断变化是改善还是退化，不能直接更新基准图让错误通过。

局部小修可以由同一 Agent 在实现后切换为用户视角审阅。跨层能力、共享契约或迁移变更，以及反复被用户补报关联缺口的工作流，执行[交付方法第 3 节](hhpi-delivery-method.md)的独立上下文审阅：先看原目标、原生基线和实际画面/操作，保存应有行为与疑点，再对照实现清单。委派权限、暂不可用时的状态和复核范围按该节处理；同 Agent 换视角不能冒充独立评估。

### 第五步：记录、修复，再走原路径

问题记录最少包含：触发入口与状态、来源/视口类别、实际结果、期望结果、证据位置、影响、对应模块与下一步。分类为“源码疑点”“视觉确认”“交互复现”或“源端结果确认”，不能把模型对截图的猜测直接写成已定位根因。

记录顺序是“观察到什么 → 用户受什么影响 → 核对操作与产品归因 → 处置”。按钮第一次无响应时保留该观察；后续确认是误点可标明并关闭，绕路成功则仍保留原入口问题。已确认的裁切、明显占屏、结果丢失或无法返回，不能因为页面还能完成别的动作而改判通过；改变严重度需给出原目标与实测依据，不能只写“影响不大”。

已授权实现中的明显问题直接修：无效入口、错误目标、遮挡、裁切、丢草稿、无法返回、结果丢失、默认诊断刷屏，都属于完整工作流的质量。若发现是官方扩展包契约问题，先核对已经获得的具体批准；已批准范围不再询问。确实超出范围才按仓库要求说明包、契约和必要性。产品方向变化另列，不借“主动检查”扩张成全面重做。

修复后在同一内容、视口和操作路径复验。涉及共享样式或 provider，再查一个实际共同使用方。数据状态问题留下精确行为回归，稳定的几何问题在既有浏览器场景补断言，信息层级问题保留简短规则和看图记录；不对每个间距调整新增一套测试。

## 5. 必须处理的“中间过程占满界面”问题

这是一项内容设计检查，不能由“没有报错”或“Process 按钮存在”代替。

| 用户需要的信息 | 默认呈现 | 检查动作 |
| --- | --- | --- |
| 当前工作与状态 | 当前推理/工具按原生策略展开，摘要可理解 | 在运行状态观察一次真实状态转移，而非只看已完成历史 |
| 已结束的过程 | 自动收起，保留概要和用户手动展开意图；普通工具失败留在过程详情，不追加正文告警 | 回放普通正文边界、新过程、完成/失败；手动展开旧过程再接收更新 |
| 正常正文、图片、计划、结果 | 保留在主阅读路径；适用动作可见 | 用混合内容检查图片、计划没有被工具组吞掉 |
| 需要用户决定的请求 | 显示对象、范围、理由与有效选项 | 同时出现多个请求，确认内容可理解且动作绑定原请求 |
| 影响用户操作的失败或持续不可用 | 保留正文和草稿，在相关入口说明影响与可用动作；自动恢复过程留在后台 | 同一路径确认内容不丢、必要动作可用、恢复后提示消失 |
| 技术细节 | 参数、完整日志和内部状态进入已有过程详情或诊断入口 | 默认画面不增加逐条诊断卡、回执块或重复原文；需要时仍可查详情 |

对 Agent 生成的普通说明，还要判断它是否增加了用户需要的信息。具体输出要求、受控源指令落点、生效范围和实际输出检查统一见[交付方法第 5 节](hhpi-delivery-method.md)，由 M5/M8 承担。客户端按源角色、类型和阶段组织内容，普通正文保持忠实；源端减少重复说明和客户端正确折叠分别留下证据。不可控源的限制明确记录，不能通过任意删除正文或伪造消息类型掩盖问题。

对同一混合内容片段分别验收数据和默认呈现：图片及计划确实接入只是前半程；默认画面还须使用户能找到当前工作、主要结果、待决定事项和下一步操作，历史诊断不能持续挤走这些内容。审阅先说明这四类信息在哪里、是否需无谓滚动或展开，再看组件是否渲染成功。不用自动截图分数或 DOM 元素存在替代这一判断。

## 6. 两条发布场景如何容纳这些检查

继续遵守[现有两条发布场景](testing.md)：桌面两会话、手机视口，每条 60 秒。`test:smoke:history`的两个上下文已经使用这份预算；不能再偷偷叠加两条 UI 流程，也不能把实验室通过充当生产站点通过。

实施前为本次切片写出要进入的页面与状态，把最关键的受影响入口嵌入相应场景。状态竞争、回执与作用域尽量由组件/契约测试验证。视觉检查针对实际采集的目标状态；截图采集次数和耗时继续按现有规范，不为每行清单开一套浏览器。

若必要布局/交互检查无法在现有场景和预算内完成，缩小实施切片，把未验证部分保留在整体交付清单，不能借此删掉产品目标。不能删掉现有连续阅读断言、延长超时、拆成多个“本轮”规避上限，或把“抽查过”写成“全部没有问题”。物理手机/软键盘和真实后台通知是明确的验收任务，由 Agent 发现设备、执行并修复；未执行时不能宣称整体完成。

完整基线仍不做无限组合漫游。入口可以一次盘全，运行检查随真实实现切片推进；第 6 节 A1–P4 表最终必须有具体证据或明确不适用依据。主方案另提出两段各 60 秒的一次性设备验收任务，分别覆盖输入法/键盘与后台通知返回；这是显式的补充安排，不能算作现有两条发布浏览器检查已经覆盖。实施前按现有规则明确新增设备预算，必要时处理具体规则调整。本轮不修改测试规范或执行额外产品检查。

### 真实手机检查的判据

| 实际操作 | 必须观察的结果 | 不能替代的证据 |
| --- | --- | --- |
| 中文输入、选择候选、换行、发送 | 候选确认不提交；换行符合设置；显式提交一次且属于当前会话 | jsdom composition 事件、直接插入中文字符串 |
| 草稿附图，依次打开候选与设置菜单并取消 | 发送可达、候选未被键盘裁切；原草稿、附件、光标与选区保留 | 调小 viewport、只看输入框出现 |
| 收起/打开键盘，旋转与切 Pane 再返回 | 正文空间和底栏恢复，历史位置与输入目标不乱 | 最后一次截图看起来正常 |
| 手机终端输入、控制键、粘贴与 resize | 同一源 PTY 正确接收，输入不重复；返回聊天不误关终端 | command/exec 返回文本 |
| 退后台收到隔离任务通知并点击 | 实际系统通知可见，进入原请求；已结束请求显示结算事实 | Push API 成功、前台 toast、合成 notificationclick |

设备、系统、浏览器、输入法、构建和来源版本必须记录。现有 viewport 与 IME 保护作为起点，发现的是哪一层缺陷就修哪一层，不为“必须修”凭空重写原生编辑器。

## 7. 如何证明主动发现已经发生

每个实施切片使用[交付方法第 4 节的同一执行记录](hhpi-delivery-method.md)，不另建 UI 完成表或仪表盘。UI 部分补入本次内容与状态、真实入口到二级页面及返回、交互对象与结果、已经打开查看的截图及具体判断、主动发现与同路径复验，以及尚未检查的页面/来源/设备。沿用行为 ID 和 A1–P4 / M0–M8 / R1–R10 归属；实现状态与验证状态分别记录。

必须能从记录回答“打开了哪个二级页面、看到了什么、为什么判定可用”。只有截图文件名、测试数量、HTTP 200 或“UI 已检查”不算。

影响判断按用户结果：误操作、数据丢失、关键路径不可用或主要控件不可达，必须在相应功能宣布完成前处理；明显占屏、诊断刷屏、默认内容层级错误也是本次体验问题，不以“还能点击”为由搁置。细小审美偏好可记录，不让无关重设计阻塞已验证修复。没有强制“至少找出几个 bug”的指标，避免凭空制造问题。

方法是否减少遗漏，按[交付方法第 6 节](hhpi-delivery-method.md)在后续尚未被逐项提示的跨层任务上观察：首次交付后的用户补报、同类复发、体验回退、重复确认、实际行为覆盖、审阅耗时和误报。二级页面的发现来源与未检查状态单列。旧截图和已知问题只能作回归；没有用户反馈或没有发现问题，不能直接证明方法有效。

## 8. 本轮文档修订的边界

源码路径指向当前基线；实施后以新模块及实际证据更新，不将删除后的 HAPI 文件当作必须保留的组件。

本方案把主动检查前移到 M0–M8 每个功能切片。此前修订纳入来源退役、迁移、独立查漏和源端输出；第八次修订进一步区分到达状态、看图判断与实际结果，补充生命周期组合、重开窗口和异常处置。文件保存、可靠终端、后台通知和真机键盘继续纳入完成标准。本次没有运行产品检查，也没有证明当前线上 UI 已无缺陷。

本轮不修改产品源码、HHPI 协议、测试脚本、AGENTS 规则、依赖或发布配置。文档图文页的渲染与交互验证只证明这份报告可读。
