# 连续历史阅读的架构调整

本文记录 V4 的窗口与读者调整。HHPI 为 DSH Web 提供通用 Agent 远程接入，无需依照 HAPI 架构；下一步去掉重复事件转换的方案见 [HHPI 远程接入架构](hhpi-remote-access-design.md)，不代表当前已接通。

目标是像阅读同一份完整对话一样连续前后移动。历史可以分页、缓存和释放，屏幕也可以虚拟化；这些资源边界不能表现为两段对话之间的跳转。

## 源码对照与原因

HAPI 的 `web/src/lib/message-window-store.ts` 先合并原始消息，`sliceForTrim` 在未达到窗口上限时保留原内容。向前、向后的读取均提供发布前回调，`web/src/chat/nativeViewport.ts` 在提交时重新采集当前阅读锚点，并通过同一 viewport 恢复。HAPI 也有界，连续体验来自消息身份、发布边界和阅读控制的一致性，不能归结为窗口无限大。

hapi-dsh 原路径有三处冲突：

- `sourceRetentionPlan` 把可见区前后各六个源组当成正文保留范围，即使全部内容仍低于事件和字节上限，也删除已读正文。源记录数与工具折叠后的页面高度没有对应关系。
- `trimWindow` 对普通分页、实时更新和无变化都发布全量 `replace`。官方 assembler 重建正文分组，`reading-view` 又把它当重连恢复，重新发起定位。
- 向后读取直接修改数据窗口，未进入与向前读取相同的官方阅读锚点提交路径。几何上的滚动到底，也不能表示已经抵达远端会话的最新消息。

上述为源码因果分析；不据此宣称性能倍数或已达到 HAPI 的长期可用性。

## 确定的调整方向

正文路径收敛为：源消息及共享页缓存 → Pane 自己的连续游标窗口 → 纯展示投影 → 官方 Conversation → 同一官方 viewport 的提交与位置修正。Host 的已投影页 LRU 总量 32 MiB、单源 8 MiB、最多 8 个源；客户端按 HAPI 的 800 条历史窗口裁剪源组，并以 8,000 个事件和 8 MiB 限制展示投影。可见 Pane 与当前整页优先保留，被裁剪的连续区间通过源游标回读缓存页。

执行仍归同一个原生 Agent 和 Session。正文读取不创建执行运行时，关闭阅读窗格不终止执行。消息身份由 HAPI 的 message id、源游标和正文版本决定；客户端数字序号只用于当前投影。

每个 Pane 管理自己的阅读游标、请求取消和位置，共享不可变页数据。客户端页仓库按原会话、历史版本和源游标复用已接受的 HAPI 页，沿用 HAPI 的 32 MiB 全局、8 MiB 单源、8 个源的 LRU 上限；它不把原始记录和投影帧重复保存。预取页与视口需要的条数不同时，缓存按源消息身份切出最近的一段，并把未消费部分留给后续游标，避免条数变化取消预取、重新读取同一历史。正文修订只失效涉及的页，历史重写清空该源的页，窗口被裁剪或 Pane 重新打开仍可从缓存补回。两个 Pane 阅读同一会话不同位置时，不以一个可变正文窗口强迫它们共同裁剪或共同跳转。

交互式上翻每次按 50 条 HAPI 常规原始消息页提交；首屏填满视口仍使用单独的 20/80/200 自适应读取。DSH 会把原始消息展开成多个展示事件，因此可见阅读窗安装后预热相邻页，并在每页提交后继续预热一页，避免让用户等待当前请求。不能让普通一次上翻因寻找 turn 边界而扩大成最多 500 条，再让一次 React 提交承担额外投影事件。

投影负责稳定节点身份和消息修订，不以屏幕 overscan 决定删除源消息。预算内保留已经收到的连续内容；真正达到预算时，从远离当前阅读位置的一侧释放。折叠过程的控制座位、展开状态及正文依赖需要一起保持，不能仅保住某个工具标题就算阅读位置未变。

普通扩展按批次 `prepend` 或 `append`，无变化不发布。修订、显式导航和真正的正文重写各自保留语义；普通 `replace` 不自动制造重连恢复。正文实例或版本变化仍取消迟到响应并恢复有效阅读位置。

向前与向后读取、跨预算裁剪和显式导航统一采用：准备候选窗口 → 在真正发布前测量当前官方读者 → 一次发布 → 同一官方读者修正位置。请求期间用户继续滚动时，提交使用用户最新位置；不能把请求发出时的位置强行恢复回来。普通滚动抵达历史窗口尾部只继续读下一页，显式“回到最新”才改变跟随意图。

## 实施边界

本轮先修正无预算压力的删除、全量发布和错误重连恢复，并加入连续阅读、真实预算压力及已知故障检出的回归。

普通上翻通过 `mountedChat.loadOlder()` 调用与按钮相同的官方 `ChatNavigation.loadEarlier`。源页发布前调用同一 mounted reader 的 `preparePageCommit()`，由官方 viewport 在 layout 中恢复位置；源路径不再使用 DOM 锚点补偿或固定两帧后的滚动写入。程序化操作等待实际加载和布局结束，源游标先变化不提前结算。折叠工具页没有增加可读前缀时，在向上阅读意图仍有效且仍接近边界的条件下沿同一入口继续补页；源窗口保留其容量和单次读取上限，不使用普通追加 Session 的累计页数和手势静默门槛。

HAPI 源会话逐条保留历史过程摘要，以独立消息作为虚拟列表单位；工具详情仍由各自的展示组件管理，不再把整轮过程藏在一个“已完成”控制后面，也不把整组消息作为一个巨大的虚拟行。否则一个长 turn 内的许多数据页均没有可读高度，数据游标推进也会表现为原地加载。普通 DSH 会话保留原有整轮折叠偏好。

共享 Client 图必须注册 mounted-Chat consumer，按回调中的实际 Chat 根元素找到所属 Portal 和 Pane；相同 Session 的多个出现位置仍各自持有读者，离屏预备视图不覆盖可见读者。旧独立 Pane 图的注册不能代替共享路径的注册。卸载仅清除仍属于该出现位置的句柄。

完整的 Pane 窗口替换仍应接入官方 `historySource`、`windowCommit` 能力；当前源窗口主路径尚未完成这项迁移。`dsh-ext/ext/adr/0001.md`、`0003.md` 与 `0007.md` 分别描述独立窗口、原子替换和 mounted reader 提交。普通 prepend 的统一不等同于完整迁移；接入与上线情况以实际验证为准。

完成条件包括：真实长会话连续补页后往返阅读，内容顺序连续、可见阅读锚点稳定、已读区间不反复拉取；工具折叠、实时更新、迟到响应和双 Pane 各自成立。数据提交成功与阅读位置修正成功分别判定。单元测试、HTTP、一次滑动和截图均不能代替实际连续阅读。
