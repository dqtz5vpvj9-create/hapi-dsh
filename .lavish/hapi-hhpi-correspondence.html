CORE READER · HAPI ↔ HHPI · SOURCE-BASED

同样是读聊天，HHPI 改掉了什么？

HHPI 绕开了旧 HAPI 消息往返，由接入侧适配一次，再交给官方 DSH 读者。
它仍使用 DSH 事件模型，未变成“原始消息直接渲染”。

关键变化：阅读数据与原生执行分开

HHPI 的数据缓存、Pane 阅读外观与官方 assembler 都是展示侧对象。原生 Agent 继续负责执行、队列和审批；关闭 Pane 释放读者，不结束 Agent。

与旧 V4 相比，退出主链的是哪些层？

HAPI 消息 → Host projector → SourceFrame → SourceWindowStore 重新编号 → SourceEventFeed → 官方 assembler

HHPI Codex 主链改为 原生 item → CodexHistory / SourceEventIndex → SourcePage / SourceChanges → 官方 assembler。旧兼容模块仍在仓库，未画成已经物理删除。

仍然存在：DSH 事件兼容

网络页的 SourceEntry.event 仍是 SessionEvent。CodexHistory 仍需表达 turn/start、step/start、message、tool 和结束边界。只是在接入侧确定一次身份与顺序，翻页与浏览器不再重新分配。

仍然存在：两种 SessionFace 外观

RemoteSourceSession 对接源能力，RemotePaneSession 对接独立官方读者。这些外观不创建 DSH 执行 Session 或 Agent。它们仍带来初始化与释放时序，不能说已经没有适配成本。

DSH 和 Codex 不必走同一种适配

DSH 复用原生 federation / provider 路径；Codex 实现 HHPI SourceAdapter。其他引擎已有适配接口，不能据此宣称已经完成接入。

当前生产边界

本机与 Windows 的 Codex 已配置 HHPI 直连接入；两个旧 DSH Pane 保留原引用，尚未迁移成可用的 HHPI 观察路径。离线 Runner 也不能画成已经在线。打开原生 DSH 冷会话可能触发 resume，这与只读历史接入不是同一个语义。

一次翻页，由谁负责到最后？

1 · 官方导航发起

边界触发与按钮选中同一个 Pane 的 mounted Chat / readingView。

→
2 · 数据窗口准备

RemoteHistoryWindow 命中缓存或读取源页，生成候选连续窗口。

→
3 · 官方窗口提交

BoundHistoryView 用私有 assembler 准备展示，由 windowCommit 协调发布。

→
4 · 同一视口恢复

mounted Chat 采样当前锚点、恢复位置，完成后再结束请求。

原生执行与写操作走另一条路：RemoteSourceSession → SourceGateway.operate → 原生 app-server。阅读窗口换页不改变原生 thread ID、执行 owner、队列或审批归属。

架构上仍与 HAPI 不同的负担

HHPI 多了接入索引与官方事件约束

Host 保存可重建的 SQLite 事件索引，而不只是透明转发原始记录。它减少重复转换，也引入原生历史索引、版本、依赖事件和生命周期兼容的维护责任。

官方读者减少竞争，不能代替时序验证

源 baseline、Pane 引用与可用编辑器有不同准备阶段。独立 Pane 还要求输入与菜单服务按 scope 查 binding；按会话 ID 反查 canonical binding，会把合法 Pane 判成失效。阅读主链接通并不自动证明这些消费者都兼容。

③ 浏览器展示投影

HHPI 不再用 SourceFrame 转回 DSH 事件。官方 assembler 仍把 DSH 事件投影成 Chat Node；它是可丢弃的展示状态，不是第二个 Agent 执行运行时。
